## 🟡 P2 · 精度与合规

### 8. 读取域的物理隔离（⛔ 架构限制 · 不适用）

> **2026-10-21 结论：原方案在本架构下不可执行，状态改为「不适用」。以下为自包含摘要。**

| 项 | 内容 |
|---|---|
| **原要求** | ① 建低权限运行用户；② 把 `truth.json`/`spec/`/`config/`/`judges/` 设为该用户不可读（`chmod 700` + 属主为运行者之外）；③ **席位子进程以低权限用户运行** |
| **不可行的决定性原因** | 席位是 **LLM 子代理**，不是本地进程（`new_round.py:13`：「子代理只能由主会话通过 Agent 工具发起。Python 脚本无法调用」）。**第 ③ 点没有执行对象**；`chmod`/`chown` 对 LLM 读取无效——它走 Agent 工具，工具进程本身有权限 |
| **附带障碍** | 照做会让当前用户失去 `spec/`、`config/` 的读写权，而 `verify.py`/`seat_check.py`/`regress.py` 都要读它们 → **项目当场停工** |
| **替代结论（真正的边界）** | ① **真值不进入席位可读路径**这个设计约束；② 第 9 查对申报的比对。OS 层隔离在本架构下**连「降低风险」都做不到**：它防的是本地进程，而威胁来自 LLM 的工具调用 |
| **已验证可用的部分** | macOS `sandbox-exec` 可对**本地命令**做读隔离（实测：`python -c "open(truth).read()"` → `PermissionError: [Errno 1]`，EXIT=1；对照组可读 940 字节）。供「用脚本模拟席位」的场景使用，**对真实席位无效** |
| **判据差异说明** | 原判据写 `Permission denied`，实际报 `Operation not permitted`（macOS sandbox 错误码），语义等价 |

**为什么不做，而不是做不了**：OS 权限管的是本地进程，本项目威胁来自 LLM 的工具读取——两者不在一个层面。
即使把文件设成 700，LLM 仍可经工具读到。**强行实施只会破坏工作流，不产生任何防护效果。**
