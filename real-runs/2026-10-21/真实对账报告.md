| 字段 | 值 | 是否自洽 |

## 三、根因：同一类坑的**第三次**

`sim_trade.py:237-256` 有一段自述式注释，记着前两次：

| 时间 | 症状 | 处置 |
|---|---|---|
| 2026-09-01 | `market_value` 是**存储字段**，减仓后不重算 → 601668 2000→1000 股，市值仍按 2000 股算，虚高 ¥4,590 | 改为 `shares × current_price` 现算并回写 |
| 2026-10-19 | **同一个坑第二次**，这次是 `floating_pnl` | 并入同一回写块 |
| 2026-10-21（本次发现） | **第三次**：同族的 `pnl` 仍未纳入回写块 | 待处置 |

回写块现在长这样：

```python
_pos["market_value"] = _mv                       # 09-01 补
_pos["floating_pnl"] = round(_mv - _cost, 2)     # 10-19 补
# 缺：_pos["pnl"] = _pos["floating_pnl"]
```

**这不是三个 bug，是一个 bug 被逐个字段地发现。** 根因是「同一语义有多个字段名，而重算只覆盖被举报的那一个」——
与 `check_consistency.py` 里 `excluded_categories` 的问题同构：**校验只覆盖被点名的那部分**。

### 8.5 一个被我误判的「缺陷」（已更正、已改命名）

**原文（错）**：「`daily_briefing.py:127` 把 `it['pnl']`（金额）按 `{:+.2f}%` 打印，会显示成 +334.50%」。

**事实**：该处 `pnl` 一直是**百分比** `(现价 − 成本) / 成本 × 100`，`%` 是对的。**我把它当金额，误判成了单位错误。**

但这件事本身暴露了真问题：一个叫 `pnl` 的字段装着百分比，与账本里装金额的 `pnl` 同名。
**连复核者都会读错，说明名字确实有病。**

已改（`daily_briefing.py`，3 处）：

| 位置 | 改动 |
|---|---|
| 局部变量 `pnl` × 2 | → `pnl_pct` |
| 字典键 `"pnl"` × 2 | → `"pnl_pct"` |
| 渲染 `it['pnl']` | → `it['pnl_pct']` |

验证：`py_compile` 通过；`--dry-run` 实测渲染 `招商银行 持仓 +8.59%`（= 334.50 / 3,893.50，与账本一致）；
全仓无其他模块 import 该模块、无残留 `"pnl":` 键。

> **两类命名病，同一种代价**：
> 前一条 `positions.pnl` 是「两个名字、一个语义」→ 会分叉出僵尸值；
> 这一条是「一个名字、两个语义」→ 会让人读错单位。
> 两次都是我踩的，也都靠「先确认字段语义，再做判断」抓出来。

### 10.3 唯一残差：浮动盈亏差 33.09 元（费用口径，已量化到逐仓）

| 持仓 | 券商盈亏 | 账本浮动盈亏 | 残差 |
|---|---|---|---|
| 600584 | −8,771.51 | −8,757.30 | −14.21 |

| 002185 | −4,298.38 | −4,289.50 | −8.88 |
| **合计** | **−15,409.89** | **−15,376.80** | **−33.09** |

**归类裁定（2026-10-22，用户）**：这 33.09 **记入「股息入账」**，落在账本 `income_ledger`：

```json
{"date":"2026-10-22","category":"股息入账","amount":33.09,
 "source":"券商对照残差 B6（国金APP截图 10-22 07:18）",
 "detail":{"600584":-14.21,"588170":-10.00,"002185":-8.88}}
```

**登记方式与边界**：只做**收益归因**，**不改 `cash_available`、不改 `floating_pnl`**。

**算术含义（必须写清）**：归类是「说明这笔差额的性质」，不是「增加 33.09 的收入」。
因此 B6 的残差仍是 −33.09，不动。若哪天按「确实收到 33.09 股息」处理，则需同时核对现金——
而现金现在已经对平，说明这 33.09 并未以现金形式到账。

> 换句话说：**这笔差更像费用（券商盈亏已扣费），按你的裁定记为股息入账，是归因口径的选择；
> 数字上它与券商仍然差 33.09，不会被"归因"抹平。**

```
可用 ¥0 | 冻结委托 ¥0
资金利用率 0.0%
```

而真实值是 可用 9,687.98、冻结 0、利用率(股票) 58.3%、含非股票 76.7%。

### 11.2 根因：4 个键从来没有生产者

`dashboard.html` 读 `summary.utilization_stocks` / `utilization_total` /
`cash_available_actual` / `cash_frozen_by_orders`——**全仓检索无任何写入方，账本里也没有这些键**，
JS 用 `?? 0` 兜底，于是「没有数据」被渲染成「数据是零」。

`?? 0` 是最危险的一种兜底：它让缺失看起来像正常。

### 11.3 顺带发现的第二个 bug：实盘卡片用了模拟盘的数据

同一段代码用 `positions` 算实盘口径，而 `positions = pf.positions`——**那是模拟盘**。
即使把 4 个字段喂进去，算出来的也会是模拟盘的数。已一并改为 `live.holdings`。

### 11.4 修法：不新增账本字段

| 指标 | 取值 |
|---|---|
| 可用 | `summary.cash_available` |
| 冻结 | `max(0, 可用 − 可取)` |
| 利用率(股票) | `Σ(非 5 字头持仓市值) / 总资产` |
| 利用率(含非股票) | `summary.total_market_value / 总资产` |

刻意**不往账本里加这 4 个字段**：它们全是比值，加进去只会再造四个需要维护的派生字段。

### 11.5 工具配套：扫描器学会查「读但不存在」

`field_provenance.py` 新增 `--consumer-file`，解析消费方源码里的 `ls.<field>` 引用，
与账本实际键比对。首次运行报 4 处缺失，修复后为 0。

**两次误报暴露了正则的粗糙**（已修）：
- `labels.push(...)` 被误识别为 `ls.push`（前缀前缺边界）；
- 注释里的旧字段名被当成引用（未剥注释）。

## 十二、自查发现的隐患：盘前刷新会把 `daily_pnl` 抹成 0（已修，`8ef3146`）

> 这一条不是数据错，是**我自己上一个修复引入的边界风险**——由「换场景想一想」发现，不是由工具发现。

### 12.1 风险

`daily_pnl` 改为「Σ 涨跌额 × 股数」后：盘前/休市时现价 = 昨收 → 涨跌额全为 0
→ 若照写，会把上一交易日的 −166.00 覆盖成 **0**，界面从早到晚显示「日 ¥0」。

### 12.2 修法

**全部标的涨跌额为 0 时不写**，保留原值并打印告警。

代价：真正平盘的一天会保留旧值（次日刷新覆盖）。
取舍理由：保留一个已知为真的旧值，优于写入一个已知会误导的 0。

### 12.3 回归

新增两条测试（`tests/test_refresh_portfolio.py`，共 11 passed）：

| 用例 | 断言 |
|---|---|
| 涨跌额全 0 | `daily_pnl` 保持 −166.00 不变 |
| 涨跌额 −0.42、100 股 | `daily_pnl` = −42.00，且 `prev_close` = 现价 + 0.42 |

### 12.4 这条为什么值得记

前四条缺陷都是「**已有**的错」，由工具扫出来；
这一条是「**将要**发生的错」，工具扫不出来——它只需要换一个时间场景想一想。
**修复引入的新风险，不会出现在任何存量扫描里。**


### 11.7 第五个同类问题：标题日期取错字段（2026-10-22 11:17，由截图发现）

用户按要求打开看板核对，四个数字（9,687.98 / 0 / 58.3% / 76.7%）**全部正确**，
但暴露出标题写着「国金 · **2026-10-11** 截图」——而价格其实是 10-21 刷新的。

**根因**：`srcDate` 从 `data_source` 里抠日期，而那个日期是**结构确认日**
（当天截图显示的是更早的 10-09 收盘），不是数据时点。**同一字段被当两个语义用。**

**修法**：改取 `prices_refreshed_at`（行情真实刷新时刻），缺失才退回 `data_source`；
文案由「截图」改为「行情 as-of」——因为现在的主体是刷新后的行情，不是那张截图。
顺带统一金额格式（`toLocaleString()` 对 47,340.8 只留一位，与 41,651.98 不一致）。

**这条的意义**：前四条是读代码/跑工具发现的，这一条**只有真的打开页面才看得见**。
静态分析能证明"数字取对了"，但证明不了"标签说的是不是同一件事"。
