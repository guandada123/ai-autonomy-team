# L-0028 固定窗口的单次观察是易失源，「没看到」≠「没发生」

**日期**：2026-10-25
**标签**：观测方法 / 误报 / 元监控
**状态**：已验证（差点造成一次真实误报，被"不升级为结论"的纪律挡下）

## 发生了什么

08:05 的「看板巡检」自动化按 prompt 规定「无异常则不落文件」。08:22 我查看
`outputs/inspection-2026-10-25.md` 不存在，结合昨日报告列的异常条件仍在，
**倾向判定"巡检未跑/失败"**。

08:30 复查：报告在，mtime 08:26——巡检 08:22 才开始写、08:26 落盘。
**我 08:22 查看的时刻，它正在写。** 「文件不在」的真实原因是窗口太早，
不是故障。

## 教训

1. **"产出缺失"类判断，观察时刻本身就是判据的一部分**。对耗时不稳的
   LLM 任务，单次 `ls` 的置信度约等于零；要么等一个覆盖其耗时分布的
   宽限窗口，要么看 mtime/进程等过程证据。
2. **当时做对的一件事：没有定性为结论**，只登记"待复核、明日同窗判别"。
   如果据 08:22 一眼定案并写进报告，就是一条**凭空产生的故障记录**，
   后续所有基于它的决策（加告警、改调度、问责）全部建在沙子上。
3. **元监控的核对点必须后置于被观测者的耗时分布**：本次元核对定在
   09:10（08:05 触发后 65 分钟 = 实测迟到 21 分钟的 3 倍余量）。宽限
   不够的元监控只会生产"狼来了"，消耗真实告警的可信度。
4. 配套设计：核对判据不能只问"文件在不在"（单指标），要复检"异常条件
   是否仍在"——条件消失则缺文件是正常的（无异常不落文件）。参见
   `scripts/inspection_watch.py` 预注册判据。

## 复用方式

- 建任何"某任务是否跑了"的核对前，先测量该任务的**触发→落盘耗时分布**
  （至少 3 个样本），核对点取 p95 以上。
- 报告里写"未观察到 X"时必须带**观察时刻与观察方法**；两者缺一条，
  该结论不可被他人复现或推翻。
- 与 L-0017（对照须同信息条件）同源：观察窗口不同 = 信息条件不同。
