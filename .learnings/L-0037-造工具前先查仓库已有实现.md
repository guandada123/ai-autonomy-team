# L-0037 造工具前先查仓库已有实现——审计建议里点名的文件往往不是空想

**类型**：★ 升级候选（跨项目通用） 〔🔁auto-promote-2026-11-22·✅已评估·同族覆盖→「造工具前先查已有」〕
**性质**：跨项目通用（任何多人多会话协作的仓库）
**状态**：已实测（本日 ai-autonomy-team 两次险些重造，均被当场拦下）

## 发生了什么

P1 任务「手写计数生成器化」。我按审计建议动手，**两次**差点造出重复工具：

1. 看到 `scripts/sync_doc_numbers.py` 存在但只管 MANIFEST 字节数，于是往里扩展了
   COUNT_FIELDS（kit 数 / 决策范围 / 备份体积等）——写完才发现 Makefile selftest 里
   已有 `handover_facts.py --self-test`（另一个并行会话**同一天**新建的生成器，
   职责完全重叠：kit 数、决策/经验数、覆盖率基线，且已进门禁 F 类校验）。
2. 第一次更早：直接新建 `scripts/sync_doc_numbers.py` 被 Write 冲突拦下——
   才发现 10-23 就有同名文件。

自检倒是没白做：首跑就咬到真 bug（编号回写丢零填充，`D-0080`→`D-80`），
但这套逻辑最终没有入库——**重复实现不入库也是正确产出**。

## 根因

动手前只查了「同名文件」，没查「同职责工具」。工具名可以不同、职责可以重叠，
`ls scripts/` 排查不了后者；而并行会话当天新加的工具，文档里可能还没来得及提。

## 判断规则

1. 造新工具前三连：`grep <关键词> Makefile`（selftest 收编列表）+ `ls scripts/` +
   `git log --oneline -20`——三处都没命中才动手。
2. 审计/交接文档里写「`xx.py` 类工具」且与任务同名的，**先读它**——名字命中往往不是巧合。
3. 发现重复后按铁律「同一语义值须单一真源」裁决：保留**被门禁收编**的那个
   （handover_facts.py，F 类校验 + make selftest），撤销未收编的（我的 COUNT_FIELDS）。
4. 判断「工具是否已存在」的成本是一次 grep；双实现并存的成本是两套正则各自漂移、
   门禁 A 与 F 类互相打架。
