# L-0036 并发缺陷是分层的，修好第一层才会露出第二层

**日期**：2026-10-29
**标签**：并发 / 共享可变状态 / 验收方法 / 假绿
**性质**：跨项目通用（任何「多实例共用一份 scratch / 临时目录」的脚本套件）
**状态**：已实测（ai-autonomy-team F8：regress 超时 + scratch 隔离）

## 发生了什么

F8 的目标是修「回归 scratch 路径固定，并发互相覆盖」（D-0049 早就记了、一直没做）。
做完「按 运行时间戳+pid 隔离目录」后，我用 3 个并发实例验收，结果 **2/3 红**：

| 第几层 | 共享资源 | 表现 | 修法 |
|---|---|---|---|
| 1 | `_trash/tmp-regress/`（fixtures / out / p42-live…） | out 文件互相覆盖 | scratch 根加 `<时间戳>-<pid>` |
| 2 | `migration-package/.precheck_write_probe`（固定名） | A 先 `unlink`，B 的 `unlink` 抛 FileNotFound → 记「目录不可写」→ 第 11 项红 | 探针名加 pid |
| 3 | `_trash/tmp-regress/t20-selfcheck`（固定名） | 一方写的 verdict 被另一方读到 → 第 49 项红 | 目录名加 pid |

每修一层，下一层才浮出来。**读代码看不出第 2、3 层**——它们藏在被调用的别的脚本里。

## 教训

1. **「并发安全」只能由并发实跑验收，不能由读代码确认。** 我改完第一层时，代码看起来完全正确
   （每个 write 都指向 TMP），而实际上还有两个固定名资源在别的文件里。
2. **并发缺陷是分层的：修好第 N 层，第 N+1 层才可见。** 所以验收不是"跑一次并发"，
   而是"每次修完都重跑，直到连续 3 个实例全绿"。一次绿不算绿。
3. **断言"孙进程已死"是假绿。** 最初 killpg 用例只查 `os.kill(pid,0)` 是否失败。
   把实现退回 `p.kill()` 做变异测试时它照样绿——因为只杀父进程时 `communicate()` 会一直等
   孙进程释放继承来的管道（实测卡 120 秒），等孙进程自己睡醒退出后就成了"已死"。
   正确写法：**同时**断言「及时返回（<8s）」+「孙进程寿命远长于测试窗口（600s）」。
   → 一般化：**验证"被杀死"必须验证"不会自己活到寿终"，两者缺一即假绿。**
4. **固定名资源要用 grep 主动清点，不要撞一个改一个。**
   `grep -rn "_trash" --include=*.py` 一次就能列全；逐个撞的代价是每轮都要 12 秒 × 3 实例重跑。
5. **旧版同场对照廉价且有力。** 把 HEAD 版本 clone 到 /tmp 跑同样的 3 并发：**3/3 全红**
   （红在第 11/46/49/52 项），新版 3/3 全绿。这比"我认为会冲突"有说服力得多。
6. **收益是双向的**：隔离之后，`move_stale_fixtures`（把"源已不存在"的旧夹具改名到 stale-*）
   这一整套机制**结构上不再需要**——每次都是全新复制的目录，不可能有陈旧文件。
   它的历史产物是 `_trash/tmp-regress/` 下 **225 个 `stale-*` 目录（31MB）**，
   即"用一个补丁掩盖另一个补丁的副作用"的典型代价。
