# L-0007 ★ `set` 的迭代顺序随 PYTHONHASHSEED 漂移，排序必须带完整 tie-break

- **日期**：2026-10-19
- **触发**：修完 F6 后，`new_round.py` 重跑幂等仍失败，但只有 1 个文件不稳定：`presentation/redaction.json`
- **缺陷编号**：F12

## 现象

同一轮次目录、同一输入，连跑两次开轮器：

```
第 1 次 targets: [... "config/", "judges/"]
第 2 次 targets: [... "judges/", "config/"]
```

内容一字不差，**顺序不同** → sha256 不同 → 幂等判定失败。

## 根因

```python
return sorted(set(t), key=len, reverse=True)   # 只按长度排序
```

`config/` 与 `judges/` 长度**都是 7**。`sorted` 是稳定排序，但它的**输入**是 `set`，
而 `set` 的迭代顺序由字符串哈希决定 —— CPython 对 `str` 默认启用哈希随机化
（`PYTHONHASHSEED` 随机），**每个进程不同**。

于是「等长元素」的相对顺序每次进程启动都可能变。

## 修法

```python
return sorted(set(t), key=lambda s: (-len(s), s))   # 长度降序 + 字典序兜底
```

`(主键, 完整次键)` 的形式让排序成为**全序**，与输入迭代顺序无关。

## 通用化

> **只要对 `set` / `dict` 的键做排序，`key` 就必须构成全序。**
> 「看起来稳定的输出」在跨进程时可能不稳定，只在同一进程内重复调用才稳定。

三个高发场景：
1. 排序键是**长度**或**计数**（大量并列）
2. 排序键是**浮点**（精度并列）
3. 用 `sorted(d.keys())` 但键是**对象**（按 id 排序，每进程不同）

## 检测手段（比“记住要小心”可靠）

**「同一命令连跑两次，输出文件 sha256 必须相同」** 是最省力的探测器。
本轮就是被开轮器的幂等检查抓住的 —— 它在设计时被当作「防重复写入」，
实际顺手抓到了一个非确定性 bug。

## 代价与边界

- 加次键会让「长前缀优先」的语义仍然成立（主键不变），仅在同长时变得可预测。
- 无法发现「值相同但表示不同」（如 `1.0` vs `1`）这类差异，那属于序列化层问题。
