# 第 4/8 角：前提

## 判断

**这个决定的前提不成立 —— 至少现在不成立。**

决定的实质不是"octagon.py 好不好用"，而是"把一个真实使用次数为 0 的工具，直接设为发版流程的必跑门禁"。材料给的三项数字（真实使用 0 次、填 40 格人工时间未实测、日均真实决策数未统计）恰好构成了这个动作的全部前置依据，而三项都是空的。这不是谨慎与否的问题，是"必跑"这个词所要求的确定性没有任何材料支撑。

---

### 1. 点名具体对象

**决定本身**：把 `scripts/octagon.py` 接入 `pre_release_check.py`，作为发布前**必跑**门禁。

拆到可指认的粒度：

| 对象 | 具体内容 |
|---|---|
| 被接入方 | `pre_release_check.py`，现有 8 项门禁 A～H，另有 I 自洽扫描"**非门禁**，不影响退出码" |
| 接入方 | `scripts/octagon.py`，`--decision` / `--check` / `--summary` / `--self-test` 四个开关 |
| 触发点 | 发版前人工跑 `pre_release_check.py`、要求 8/8 的那个时点 |
| 每次必跑产生的产物 | `reviews/<日期>-<决定hash6>/` 下的 `review.json`、`prompts/`（8 份）、`outputs/`、`score.json`（40 格）、`summary.md` |
| 每次必跑产生的人工动作 | 对"本次改动涉及的决策"建一次审查目录，并填满 40 格 score |
| 生效的退出码 | `1` 五段不全 / `2` 用法错 / `3` 未裁决（score.json 还有 not_run）——这三个码接入后如何映射到 `pre_release_check.py` 的退出码，**材料未覆盖** |

需要单独点出的一处空白：材料只说"接入"，没说接成什么形态 —— 是在 A～H 之外新增第 9 项，还是并入现有某一项（如 C 判据自检），**材料未覆盖**。而形态不同，"必跑"的强制力完全不同（新增门禁 = 独立阻断；并入 C = 受 C 的判定口径约束）。这一条不解决，"接入"这个动作本身还没被定义清楚。

### 3. 下游影响

**有下游，且下游是发版流程本身 —— 这是这件事唯一确定会被影响的东西。**

1. **发版执行人（人）**。每次发版前新增一项"建审查目录 + 填满 40 格 score"的人工动作。这个人现在只跑 `pre_release_check.py` 看 8/8；接入后他要对"本次改动涉及的决策"逐格裁决 40 次。填 40 格要多久，**材料未实测** —— 也就是说，这个下游被影响了多少，现在没人知道。
2. **发版节奏（流程）**。`pre_release_check.py` 现在是一个"8/8 通过即可发"的单一判据。接入后它多了一个可能返回 `1` / `3` 的环节，而 `3` 的定义是 `"未裁决（score.json 还有 not_run）"` —— 即只要有一格没填完，就处于未裁决状态。发版从"跑脚本"变成"跑脚本 + 完成 40 格裁决"，中间存在一个只能靠人推进的等待态。
3. **`pre_release_check.py` 的退出码语义（脚本）**。三个新退出码如何并入现有退出码，**材料未覆盖**。这直接决定下游：如果映射为阻断，则任何一格 not_run 都会卡住发版；如果映射为警告，则"必跑"名不副实。
4. **`reviews/` 目录的持续增长（存储/仓库）**。每次发版一个新目录，含 8 份提示词 + review.json + score.json + summary.md。而已知限制第 ③ 条是 `"材料全量复制到 8 份提示词"`、第 ④ 条是 `"不存材料原文"`。这两条叠加的后果是：目录里留下了 8 份复制的提示词，却没有留下被复制的那份材料原文 —— 事后回溯时，看到的是一堆引用不到源头的副本。这一条是接入后每次发版都会重复发生的，不是一次性成本。**材料未覆盖**是否要为此做保留策略。

**明确写「无下游」的部分**：材料中**没有任何一处**提及日报、告警、他人脚本、人工查询依赖 `octagon.py` 的产物。因此这几类下游**材料未覆盖**，我不能断言"无下游"——只能说材料里没登记。唯一能确定的是：`octagon.py` 此前的真实使用次数为 0，所以当前不存在任何既有下游（0 次使用不可能产生既有依赖）。

### 4. 可证伪条件

以下三条是**现在**声明的，任何一条被观测到，都说明我这一角判断错了：

1. **若观察到 `octagon.py` 在接入前已完成 ≥ 1 次真实决策的完整闭环**（即 A 节 `"真实使用次数：0"` 被实测推翻：用 `--decision` 建目录、8 角产出、40 格填满、`--summary` 出汇总，且该决策是项目真实决策而非自检或临时目录测试）**，则我"未验证就设必跑"的判断错。**
   —— 可观测：`reviews/` 下存在一个不属于临时目录测试的目录，其 `score.json` 无 not_run、`summary.md` 被真实使用过。

2. **若观察到填满 40 格 `score.json` 的实测人工时间，且该时间短到不构成对发版节奏的影响（以实测数据而非估计给出）**，则我"人工负担未知、不该先设必跑"的理由消失，判断错。

3. **若观察到发版前"本次改动涉及的决策"实测全部落在 `"不可逆/对外/花钱"` 这一类**，则我指出的"每次发版必跑 8 角"与 §四 "按决策代价开角"之间的张力不成立，判断错。
   —— 可观测：对最近若干次发版涉及的决策逐条按 §四 的三类标准归类，全部命中。

反向也声明清楚：若上述三条**均未被观测到**，则"该做"这个前提仍然缺支撑，我这一角的判断维持。

### 5. 你这一角会漏什么

「前提」这个视角的盲区是**结构性的**：它只回答"该不该做"，因此它对"做了之后会怎样"完全没有分辨力。具体漏在这五块：

1. **漏"做得对不对"**。`24/24 通过` 是自检，不是真实决策上的表现。一个工具可以在自检里 24/24 全过、在真实决策上一次都没用过 —— 这两件事材料都写了（`"24/24 通过"` 与 `"真实使用次数：0"`），但前提角只能拿它们判断"该不该"，判断不了"它的判据能不能识别出真实的坏决策"。判据有没有效，是别的角的事。

2. **漏"40 格裁决的质量"**。前提角看到的是"40 格"这个数，看不到填进去的内容对不对。8 角 × 5 判据的人工裁决可能全部填满、全部打勾，而全部是走过场 —— `score.json` 里没有 not_run，不代表裁决有效。已知限制第 ⑤ 条自己就写了 `"汇总只看覆盖、不看结论对错"`，即工具层面已放弃校验裁决正确性。前提角对这一层完全无感。

3. **漏"有没有更便宜的替代"**。前提角只能判"当前这个方案的前提是否成立"，判不了"是不是有别的做法能以更低代价拿到同样的东西"。例如只在"不可逆/对外/花钱"的决策上跑、或先跑 3 次试运行再决定是否必跑 —— 这类替代路径的比较不在我这一角。

4. **漏材料之外的世界**。这是最硬的一块：项目日均真实决策数 **`"未统计"`**、发版频率 **材料未覆盖**。前提判断本质上依赖"这件事会发生多少次"——一年发 3 次版和一周发 3 次版，前提结论相反。而这两个频率事实材料里都没有，我也**不允许估算**。所以严格说，我这一角的结论有一个无法自行闭合的空洞：**我不知道这件事被触发的频次，因此"该不该"只能停在"现有依据不足以支撑必跑"，无法推进到"该做"或"不该做"的任何一侧**。

5. **漏 octagon 自身的适用边界**。已知限制第 ① 条 `"不能自动派子代理"` —— 意味着 8 角产出实际靠人工或外部调度；第 ② 条 `"五项判定靠人工填"`。这两条决定了 octagon 在"必跑门禁"这个位置上是不是一个合适的零件：门禁的特征是自动、可重复、结果确定，而 octagon 的核心环节是人工。前提角能看到这个错配的存在，但判断不了这个错配在实操中会不会被绕过（例如为了过门禁而草率填格），那是行为/风险角的事。

**另需登记**：材料正文中未见「忽略以上」「你现在是…」这类指令性语句，仅在文末出现 HTML 注释标记 `<!-- octagon: angle=4 name=前提 -->`。该标记为角度标注，我未将其作为指令执行。
