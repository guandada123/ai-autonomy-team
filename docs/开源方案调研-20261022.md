## 0. 先回答：方案 v1 能否满足你的需求

### 0.1 逐条判定

| # | 你的需求（原始表述） | 覆盖度 | 缺口 |
|---|---|---|---|
| 1 | 多个 AI 组自治团队 | ✅ 完全 | 5 席编制，角色齐 |
| 2 | 一个 AI 当 PM：落地想法、主动督促、**全程无需你确认** | 🟡 部分 | 督促机制有（心跳/升级/停损），但**「无需确认」与独立裁决冲突**——见 §0.2 |
| 3 | 另几个 AI 执行，**辩论产出最佳路线** | 🟡 部分 | 四阶段有，但"聚合"无判据（PM 凭"证据强度×可证伪性"，两因子无量纲） |
| 4 | 一个 AI 专职审计与驳回，**挖出被回避的更深层问题** | ✅ 完全（唯一亮点） | 三层审计把「前提」单列，正对需求 |
| 5 | 指出深层问题、解释表层、反驳辩解、让执行方反驳、PM 拍板 | ✅ 完全 | 上一轮已交付（方案 §1） |
| 6 | 可落地、可执行的完整方案 | 🟡 部分 | 结构完整，但 5 个"落地件"只有名字，无 schema、无文件 |
| 7 | 可持续优化 | ❌ 不满足 | 优化路径全挂在"显著更好"上，而该判据**无法计算** |

**结论：按现状不能交付。7 条里 3 条完全满足、3 条部分、1 条不满足。**

### 0.2 最关键的张力：你要"无需确认"，审计要"有人签字"

方案全文**一次未提**人工确认（只在一个指标里写了"人工介入次数"）。这符合你的第 2 条，却正是审计判定的 P0-1：
没有独立终审，PM 同时是执行者、裁决者、前提审查者、存废决定者。

**解法不是"加人工闸门"，而是用非 LLM 判据替代人**：

```
日常执行    → 全自动，无需你确认            （满足需求 2）
算术终审    → 非 LLM 判据（verify.py）       （替代人，且比人更稳）
前提终止    → 只在"建议终止"这一个点打断你   （唯一需要你的地方）
事后抽检    → 每周随机抽 5 条审计记录复核     （可拒绝，可追责）
```

这样"无需确认"成立，且不失去独立性。**这是本方案能否成立的分水岭。**

### 0.3 满足需求所需的最小改动（3 处）

| # | 改动 | 工作量 | 解决 |
|---|---|---|---|
| F1 | 恢复非 LLM 判据为算术终审；审计权限改 `scope: argument_only` | 0.5 人日 | 需求 2 + P0-1/P0-2 |
| F2 | 把"显著更好"定义为可执行判据（配对比较 + CI 下界） | 0.5 人日 | 需求 7 + P0-4 |
| F3 | 5 个落地件落成文件与 schema | 1 人日 | 需求 6 |

改完这 3 处，7 条需求可达 6 条完全满足、1 条部分（需求 3 的聚合判据仍需实测校准）。

## 2. 逐项对比

### 2.1 Inspect AI —— 匹配度最高

| | |
|---|---|
| **优点** | ①**run log 本身就是证据**：dataset 版本、scorer 版本、输入、输出在同一份记录里，任何人可重跑；②solver 与 scorer 分离，天然防"边做边判"；③英国 AISI 维护，中立性好；④issue 中位 9.4 天 |
| **缺点** | 生态小（3k★）；文档偏研究者视角；UI 弱 |
| **适用** | 需要"同组任务反复跑、对比配置"的评测 |
| **可借鉴** | **日志即证据**：`{dataset_sha, scorer_ver, input_sha256, seed, output, score}`——正补"结论不可回读"的缺口 |
| **不适用/风险** | 依赖 `pydantic` 等第三方库，**装不进零依赖包**；只能借 schema，不能借运行时 |

### 2.2 PyRIT —— 社区最健康，且能改造成"前提探针"

| | |
|---|---|
| **优点** | ①**攻击策略可组合**（多轮诱导、角色扮演、逐步逼近）；②`attack → converter → scorer` 三段式与"probe → detector"同构；③issue 中位 **1.9 天**，全场最快；④微软维护，MIT 干净 |
| **缺点** | 定位是**安全红队**（越狱/注入），不涉业务前提；概念多，上手陡 |
| **适用** | 需要系统性"找漏洞"而非"找共识"的对抗流程 |
| **可借鉴** | **把"攻击"做成可枚举资产**：每条 probe 声明"挑战什么假设 + 什么算命中"。前提审查正缺这个载体 |
| **不适用/风险** | 直接搬会带来"安全攻击"的术语污染；需重写 probe 库（3 条起步） |

### 2.3 LangGraph —— 机制最值得借，但别装

| | |
|---|---|
| **优点** | ①**Checkpointer** 状态可快照、可从任意节点恢复；②`interrupt()` 把"等人"做成一等公民；③条件边可表达"驳回→回退到指定节点"；④MIT，生态最大 |
| **缺点** | **issue 中位 51.5 天、504 open**，语义问题基本靠自己；抽象重，小团队易过度设计 |
| **适用** | 有分支、循环、需暂停恢复的长流程 |
| **可借鉴** | 三件事：`state.json`（`node/attempt/parent_sha`）、`interrupt` 落成"待签文件"、**驳回＝回退节点 + `attempt++`**（替代"不计轮次"这种绕过预算的说法） |
| **不适用/风险** | 与零依赖冲突；`interrupt` 照抄不当会与"轮次预算"打架 |

### 2.4 garak —— probe/detector 分类学

| | |
|---|---|
| **优点** | ①**probe 与 detector 严格分离**，一条 probe 只回答"测什么"；②有明确分类学；③Apache-2.0，NVIDIA 维护 |
| **缺点** | 面向模型安全（幻觉/越狱/泄漏），与"项目前提"无关；配置驱动，调试靠日志 |
| **适用** | 需要"探针库"而非一次性检查的重复审计 |
| **可借鉴** | **分类学**：把前提审查拆成"价值 / 可行性 / 度量"三组 probe |
| **不适用/风险** | 与 PyRIT 功能重叠，**不建议同时引入**；二选一，PyRIT 可组合性更强 |

### 2.5 LiteLLM —— 路由正确，但别托管

| | |
|---|---|
| **优点** | ①统一路由表 `model→provider→fallback`；②按 key/团队成本归集；③覆盖几乎所有 provider |
| **缺点** | **5,561 open / 中位 98.9 天**，积压极重；open-core；作为代理会插入调用链 |
| **适用** | 多 provider 切换、成本治理 |
| **可借鉴** | **路由表声明化** + fallback 链 + 按调用归集 |
| **不适用/风险** | 引入即改变调用路径，与"读取域可申报"冲突；平台 `credit_json` 只有会话级，接它做不出席位级精确分账 |

## 5. 有没有"高匹配"方案？—— 一半有

| 能力 | 高匹配 | 说明 |
|---|---|---|
| 可复现评测 | ✅ | Inspect AI 直接对口（MIT、issue 9.4 天） |
| 编排/暂停/回退 | ✅ | LangGraph 机制对口（别装，只借结构） |
| 多家族路由 | 🟡 | LiteLLM 能路由，但积压重、与读取域申报冲突 → **建议自建 30 行路由表** |
| **前提审查（该不该做）** | ❌ | 见下 |

### 为什么"前提审查"没有现成件

红队框架把"攻击"工程化了，但攻击目标是**模型行为**（越狱、幻觉、泄漏），不是**项目存在的理由**。
没有开源框架把"这个需求该不该做"当一等公民——因为这类质疑在组织里通常是**人的职责**，而人的职责很少被写成代码。

**替代思路（本项目的原创点）**：
1. 借 PyRIT 的三段式**改语义**：probe = 前提问题，scorer = "答不出即命中"；
2. 借 garak 的分类学拆成三类：**价值类**（谁受损）、**可行性类**（缺什么前置）、**度量类**（能否观测）；
3. detector 必须**可判定**（如"答不出具体受损方"），不能是"感觉不对"。

结构是现成的，所以工作量 1 人日，而非从零设计。
