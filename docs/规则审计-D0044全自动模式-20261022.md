# 规则审计：D-0044「计划前置」按全自动模式（C）执行

> 审计对象：`D-0044` 计划前置 + `D-0043` 五项清单（合并称"该规则"）
> 使用方式：**C 全自动**（写进钩子/CI，缺项直接挡）
> 对照：GitHub 上做"声明式规则"的六个项目（数据 2026-10-22 17:5x 实取）

---

## 一、规则语义还原（先说清它现在是什么）

### 1.1 触发条件

| 项 | 现状 |
|---|---|
| 何时触发 | **未定义**。文中写"任何任务"，但"任务"没有判据（一次文件编辑算吗？一句问答算吗？） |
| 触发粒度 | 未定义（按会话 / 按工具调用 / 按用户消息） |
| 豁免 | 仅"不可逆或紧急"，且只需"当场说明"，**无记录格式** |

### 1.2 预期行为

```
出计划 → 讨论 → 审计计划（五问）→ 执行
```

五问：① 目标写清 ② 步骤可照做 ③ 怎么算做完 ④ 会怎么坏怎么退 ⑤ 这份计划自己漏了什么

### 1.3 输入 / 输出

| | 现状 |
|---|---|
| 输入 | **自由文本**（Markdown 表格里的一段话） |
| 输出 | **无结构**（"通过/不通过"由人判断） |
| 失败动作 | 未定义（重写？阻断？警告？） |

**一句话概括**：这是一条**给人看的规矩**，不是一条**机器能判的规则**。
按 C 全自动执行，等于把一个主观判断硬塞进自动化管线——这是后面所有问题的根。

## 三、五维缺陷

### 3.1 正确性

| # | 缺陷 | 说明 |
|---|---|---|
| C1 | **五问不是谓词，是主观判断** | "目标写清了吗"无法判定。机器只能退化为关键词匹配，"写清了"与"写了 20 个字"被混为一谈 |
| C2 | **无输入契约** | 自由文本 → 抽取靠正则 → 换一种写法就漏（今天已踩过：关键词扫全文把 6 当 2） |
| C3 | **无"通过"定义** | 五项"全过"由谁判？全自动下没人判，只能规则判，而规则判不了语义 |
| C4 | **规则有效性未验证** | 没有证据表明"过了五问的计划返工率更低"。这条规则本身还没被证伪过 |

### 3.2 边界情况

| # | 边界 | 现在会怎样 |
|---|---|---|
| B1 | 五项都填"待定/暂无/TBD" | **判通过** → 典型假绿灯 |
| B2 | 极短但合格（"停甲、乙、丙"只有 5 字） | 若用字数门槛会**误杀** |
| B3 | 极长但空话（500 字说"要重视质量"） | 若用字数门槛会**放过** |
| B4 | 走"紧急"例外 | 只需嘴上说一句，**规则即被绕过**，且无记录 |
| B5 | 中英混写 / 表格/列表混排 | 依赖中文关键词的检查会漏 |
| B6 | 计划被后续修改（先过审，再改坏） | 无"计划版本"，**审的和做的可以不是同一份** |

### 3.3 性能

| # | 问题 | 说明 |
|---|---|---|
| P1 | **延迟而非算力是瓶颈** | 全自动意味着每次任务前阻塞；若同步跑多角色审计，1–3 分钟起步 |
| P2 | 深审成本随角色数线性增长 | 8 席全开时，单次计划审计的 token/时间是 3 席的 2.7 倍 |
| P3 | 无缓存 | 同一计划反复审（讨论中改一版审一次）会重复计费 |

### 3.4 可维护性

| # | 问题 | 说明 |
|---|---|---|
| M1 | **规则无版本** | 改判据会静默改变历史判定，无法解释"上次过了这次不过" |
| M2 | **无规则自测** | 没有 fixture 集，改完不知道是变严还是变松 |
| M3 | 判据分散在两份文档（D-0043 五项 + D-0044 五问），**两处措辞不同** | 后续必然漂移 |
| M4 | 无失效告警 | 规则长期 0 拦截 = 可能已失效（今天在"假绿灯"上踩过多次） |

### 3.5 配置易用性

| # | 缺什么 | 后果 |
|---|---|---|
| U1 | 无 severity 分级 | 只能一刀切阻断 → 用户绕过（写长填满） |
| U2 | 无豁免名单 | 小改动也要走全套 → 摩擦大 |
| U3 | 无阈值可调 | 严格度写死 |
| U4 | 无失败动作配置 | 不知道是"挡"还是"提示" |
| U5 | 触发粒度不可配 | 无法区分"改个错别字"和"上线新功能" |

## 四、优先级问题清单

### P0（不修则规则必被绕过或变成形式主义）

| # | 问题 | 影响范围 | 改进建议 |
|---|---|---|---|
| **P0-1** | 五问是语义判断，机器无法判定 | 全规则 | **拆两层**：结构层（必填字段、类型、非空、非黑名单）用 error 阻断；语义层只做 warn 并交人抽检。参考 Conftest：先 schema 后规则 |
| **P0-2** | 输入无契约（自由文本） | 全规则 | 定义 `plan.json`：`goal / steps[] / done_criteria / risks[] / rollback / self_gap / exception{by,at,reason}`。规则只校验这个结构，参考 JSON Schema |
| **P0-3** | 例外通道无记录 | 可被"紧急"绕过 | 例外必须写 `exception` 对象（谁/何时/理由/补做期限），进周报；**无记录视为未豁免**。参考 OPA 的决策留痕 |
| **P0-4** | 无 fixture，规则不可证伪 | 改规则即盲改 | ≥12 条正反例（6 合格 / 6 该拦），CI 里跑规则自身；正例含"极短但合格"，反例含"全填待定"。参考 `semgrep --test` |
| **P0-5** | 计划可被事后改坏 | 审的与做的不是同一份 | 计划落盘并算 `sha256`；执行时校验哈希未变，变了则重新过审 |

### P1（影响可用性与信任）

| # | 问题 | 影响范围 | 改进建议 |
|---|---|---|---|
| P1-1 | 一刀切阻断导致形式主义（Goodhart） | 使用者行为 | 引入 severity：结构缺失 = error，语义存疑 = warn，纯提示 = info。参考 Spectral |
| P1-2 | 同步深审阻塞流程 | 每次任务 | 静态检查 <2s 同步跑；多角色深审异步，结果晚到不影响开工。参考 Danger JS 的分工 |
| P1-3 | 规则无版本 | 历史判定 | 规则带 `version`，每条判定记录 `rule_version`；升级需过 fixture |
| P1-4 | 两份文档判据漂移 | 维护 | 合并为单文件单一事实源，另一处只引用 |
| P1-5 | 规则有效性未验证 | 全规则 | 记录"过审/未过审"与后续返工，跑 4 周比返工率；无差异则降级为提示 |

### P2（体验与长期维护）

| # | 问题 | 影响范围 | 改进建议 |
|---|---|---|---|
| P2-1 | 无豁免名单与阈值配置 | 日常摩擦 | 按任务类型配 ruleset（`trivial / normal / irreversible` 三档） |
| P2-2 | 无缓存 | 重复讨论 | 同 sha256 的计划复用上次结果 |
| P2-3 | 无失效告警 | 静默退化 | 连续 20 次 0 拦截 → 提示"规则可能已失效" |
| P2-4 | 多语言/格式脆弱 | 输入多样性 | 判据只读结构化字段，不做自然语言匹配 |
| P2-5 | 触发粒度缺失 | 适用范围 | 明确：**改代码/删文件/对外发布** 触发；纯问答不触发 |

## 五、一个必须先说的判断

**全自动能审"结构完整"，不能审"计划好不好"。**

如果硬要把语义判断自动化，必然出现：
- 用户学会"填满即通过"（今天已经出现过类似的：把计划写长以过字数）
- 规则拦截率很高，但返工率没降 —— 这正是我们反复批判的**假绿灯**

所以 C 模式的正确形态是：

```
结构层（error，机器判）：字段齐、非空、非"待定"、有哈希、有例外记录
语义层（warn，人判）：目标是否真的清楚、假设是否成立
```

**机器守住"不能不填"，人守住"填得对不对"。** 这条界线不划清，全自动就是在生产形式主义。

| 步 | 动作 | 产出 | 耗时 |
|---|---|---|---|

| 5 | 4 周后看返工率 | 决定是否保留 | — |
