# 多模型辩论 · 方案调研（2026-10-22 15:3x）

> 目标：在 WorkBuddy 里真正做出「多模型辩论」，不是多个角色演同一场戏。
> 检索范围见 §6（用户要求不得草率下"没有方案"的结论）。
> 数据采集：GitHub API 实取（star / 最后推送 / 许可 / archived），时间 2026-10-22 15:3x。

---

## 0. 三条结论（先说结果）

1. **不需要装任何框架。** WorkBuddy 自带「给不同子代理指定不同模型」的能力，配置一行即可。
2. **算法可借 MoA（Mixture-of-Agents）的"提议→聚合"结构**，以及它 2025 年的升级版 **Self-MoA**——后者恰好说：**同一个模型多采样再聚合，比混多个模型还高 6.6%**。
3. **现成的 MoA 库全都停更了**（见 §2），所以只能借算法、不能借依赖——这与"零依赖"约束正好一致。

## 1. WorkBuddy 原生能力（这是关键，不是框架）

官方文档明确写了两处：

| 配置项 | 作用 | 位置 |
|---|---|---|
| `subagents.agents.<名字>.model` | **按子代理名称指定模型**，各子代理互不影响 | `settings.json` 或项目级配置 |
| `variantModels` | 把 `lite` / `reasoning` 两个别名映射到具体模型 ID | 同上 |

**优先级**（文档原文）：
`CODEBUDDY_CODE_SUBAGENT_MODEL` > **本次 Agent 调用的 model 入参** > 项目设置 > 用户全局设置 > 内置声明 > 主模型。

**这条优先级意味着**：我每次派子代理时的 `model` 参数，**能覆盖**默认模型——所以"六个角色用六个模型"在机制上是成立的。

**本机现状**：`~/.workbuddy/settings.json` 里**没有** `model` / `subagents` / `variantModels` 三项 → 全部走默认 → 实际只有一个模型。这与用户"除非人为切换"的观察一致，**但"可配置"这件事是成立的**。

> 🔴 **对 D-0035 的修正**：我当时判"跨家族不可得"，只对了一半——
> 默认不可得，**但可通过子代理配置得到**。详见 `D-0036`。

## 3. 逐项对比

### 3.1 AutoGen —— 最接近"多模型辩论"的现成结构

| | |
|---|---|
| 优点 | ①每个 agent 独立配 `model_client`，**天然支持跨模型**；②GroupChat 有"主持人"概念，可指定发言顺序；③有 `SelectorGroupChat` 按能力选人 |
| 缺点 | ①许可字段陷阱（对外写 CC-BY，代码是 MIT）；②2025 年生态分裂出 AG2；③对话式编排 token 开销大（第三方评测称 5–6×，本项目未自测） |
| 可借鉴 | **"每个 agent 一个 model_client + 一个主持人"** 这个结构，可以直接映射到 WorkBuddy 的子代理配置 + PM 编排 |
| 不适用 | 不装库：迁移包零依赖；且它自带运行时，与 WorkBuddy 的子代理机制重复 |

### 3.2 LangGraph —— 想要"可控流程"时借它

| | |
|---|---|
| 优点 | 节点级配置，每个节点可用不同模型；检查点可恢复；HITL 一等公民 |
| 缺点 | issue 积压重（中位 51.5 天）；抽象重，小团队容易过度设计 |
| 可借鉴 | **"节点 = 一个角色 + 一个模型 + 一个产物"** 的显式结构；驳回走条件边回退 |
| 不适用 | 同上，不装库 |

### 3.3 LiteLLM —— 只在需要"统一出口"时用

| | |
|---|---|
| 优点 | 一份配置管所有 provider；fallback 链；成本按 key 归集 |
| 缺点 | **5,561 open / 中位 98.9 天**，积压极重；作为代理插入调用链 |
| 可借鉴 | **路由表声明化 + fallback 链**（本项目的 `seat_contract.families` 已是这个形状） |
| 不适用 | WorkBuddy 已有模型配置，再套一层代理属重复建设 |

### 3.4 Together MoA —— 只借算法，不借代码

| | |
|---|---|
| 优点 | ①**多层提议→聚合**，结构极简（50 行可复刻）；②有完整评测脚本可参照；③Apache-2.0，引用无负担 |
| 缺点 | **21 个月未更新**；依赖 Together API；面向"回答质量"而非"对账正确性" |
| 可借鉴 | ①3–6 个提议者并行 → 1 个聚合者；②`Shuffle()` 防位置偏好；③`Dropout(0.2)` 提升鲁棒性 |
| 不适用 | 停更 + 绑特定 API，不能作为依赖 |

### 3.5 llm_multiagent_debate —— 用它的"对照实验"设计

| | |
|---|---|
| 优点 | 论文配套，实验设计严谨（有单 agent / 多 agent 对照） |
| 缺点 | 18 个月未更新；许可需逐文件核（NOASSERTION） |
| 可借鉴 | **"必须同时跑单模型基线"** 的实验结构——这正是本项目 V2 判据缺的那块 |
| 不适用 | 代码不可直接用（许可不明 + 停更） |

### 3.6 最重要的算法证据：Self-MoA

| 发现 | 含义 | 来源 |
|---|---|---|
| 标准 MoA（6 个不同模型）AlpacaEval 65.1% | 混模型有效 | Together AI 2024 |
| **Self-MoA（同一模型采样 6 次）比标准 MoA 再高 6.6%** | **单个强模型多采样 > 混多个弱模型** | Li et al. 2025（mixture-llm README 转述） |

**对我们的直接含义**：如果账号只买得起一个强模型，**"同一模型采样 N 次 + 聚合"可能优于"硬凑几个模型"**。
这给"多模型辩论"提供了一个**成本更低的替代路径**，也说明"必须跨厂家"不是硬需求。

## 4. 落地建议（按优先级）

| 优先级 | 编号 | 适用模块 | 做法 | 工作量 | 风险与规避 | 预期收益 |
|---|---|---|---|---|---|---|
| **P0** | **W0（已修正）** | 可观测性 | 扣费只能验**主线程**（实测 0 vs 12.43）；**后台任务不扣费**，故子代理改用**行为差异**判定 | 0.2 人日 | 见 `D-0038` 更正段：后台免费 → 扣费信号对子代理无效 | 不再用错信号自欺 |
| P0 | W1（**暂缓**） | WorkBuddy 子代理配置 | 写 `subagents.agents.<名字>.model`；先配 2 个不同模型 | 0.5 人日 | 配了不生效无法察觉 | 真正拿到跨模型 |
| **P0** | W2 | 六个角色 | 按 MoA 结构重排：**3 个提议者（不同模型）+ 1 个聚合者**，而不是 6 个平等角色 | **1 人日** | 聚合者权重过大 → 固定轮次 + 记录每轮输入 | 比"六个平票"更接近已验证的结构 |
| **P1** | W3 | 判据对照 | 同时跑 **单模型单次 / 单模型多采样 / 多模型辩论** 三条，比较结论差异 | **1 人日** | 样本少看不出差异 → n≥20 再判定 | 第一次能量化"多模型到底有没有用" |
| **P1** | W4 | 防位置偏好 | 借 MoA 的 `Shuffle` + `Dropout(0.2)`：聚合前打乱顺序、随机丢弃 20% | **0.5 人日** | 丢弃过多导致信息缺失 → 固定随机种子可复现 | 减少"排在前面的赢"的偏差 |
| **P2** | W5 | 成本归集 | 借 LiteLLM 的路由表思路，记录每个角色用了哪个模型、花了多少 | **1 人日** | 平台只有会话级用量 → 标"近似分账" | 回答"多模型值不值这个钱" |

**合计约 4 人日**，其中 P0 两项 **1.5 天**就能看到"是不是真的多模型了"。

## 5. 兜底：没有高匹配的"现成库"，但有高匹配的"现成结构"

| 需求 | 有没有现成库 | 判断依据 |
|---|---|---|
| 跨模型辩论的**运行时** | ❌ 没有可用的 | MoA 系列全部停更/归档（§2 数据） |
| 跨模型辩论的**算法结构** | ✅ 有（MoA / Self-MoA） | 论文 + 参考实现，50 行可复刻 |
| **让多个模型被真的调用** | ✅ 有，且是平台原生 | WorkBuddy `subagents.agents.<name>.model`（§1） |
| 辩论效果的**对照实验设计** | ✅ 有 | `llm_multiagent_debate` 的实验结构 |

**所以结论不是"没有方案"，而是**：**运行时不用找，平台自带；算法借 MoA 三层结构；验证借论文的对照设计。** 三者拼起来就是可用方案。

## 7. 风险清单（先说清，别到时候怪没提醒）

| 风险 | 表现 | 规避 |
|---|---|---|
| **配了不生效** | settings 写了模型名，但实际仍走默认 | 用一次小任务验证：派 2 个子代理，看输出风格/耗时是否明显不同 |
| **账号没有多个模型** | 配置里的模型 ID 不被识别 | 先在模型选择器里确认可见；不可见就别写 |
| **多模型 ≠ 更准** | 三个模型说得一样 | 这正是 W3 要测的；测不出来就老实承认 |
| **成本翻倍** | 每轮调用数 ×3 | 先只对"高价值任务"开多模型，日常仍单模型 |
| **许可** | AutoGen 的 API 字段写 CC-BY | 只用其结构思路，不复制代码；若要复制，读 `LICENSE-CODE` |
