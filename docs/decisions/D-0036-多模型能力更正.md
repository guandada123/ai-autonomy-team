## 依据（官方文档原文要点）

| 配置项 | 文档描述 |
|---|---|
| `subagents.agents.<名字>.model` | 「按内置子代理名称指定模型……**各子代理互不影响**」 |
| `variantModels` | 「将通用场景变体映射到模型，键为 lite 或 reasoning」 |
| 优先级 | 「`CODEBUDDY_CODE_SUBAGENT_MODEL` > **本次 Agent 工具调用的 model 入参** > 项目设置 > 用户全局设置 > 内置声明 > 主模型」 |

**最关键的是优先级链**：Agent 调用的 `model` 入参能覆盖默认模型——
说明"给不同角色配不同模型"在机制上不是靠 hack，而是官方支持的路径。

## 为什么当时判错

我只看了两处本地证据：
1. `~/.workbuddy/settings.json` 没有 `model` / `subagents` / `variantModels` → 结论"只有默认模型"（**对**）；
2. `inspect_agent_routing.py` 读不到记录 → 结论"无法验证"（**对**）。

然后把两个"对"推成了"不可得"（**错**）。
**默认状态 ≠ 能力上限**——这是本次的教训。

## 为什么不立刻恢复 min_families=3

因为**能力存在 ≠ 已生效**。三件事还没做：

| # | 待验证 | 怎么验 |
|---|---|---|
| 1 | 账号里到底有哪几个模型可选 | 模型选择器里看；配置里写的 ID 必须真实存在 |
| 2 | 配了是否真的生效 | 派 2 个子代理，用不同模型，比较耗时/风格；或找路由记录 |
| 3 | 多模型是否真的更好 | W3 对照实验（单次 / 多采样 / 多模型），n≥20 |

在 1、2 完成前把门槛升回 3，会让开轮被自己的闸门挡住——那是另一种自欺。
