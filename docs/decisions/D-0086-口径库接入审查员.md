# D-0086 · 给审查员接「口径库」（2026-10-31）

## 一、决策

四角色审查员 R1（数据核查员）/ R2（逻辑审查员）接入**口径库**，使其对"口径分歧"能给出可引用证据，而不只是"题面是否自洽"。依据：二审实验（D-0084）证明检查层信息与真值口径不相交，75 次作答 0 改动；口径库补的正是这层缺失的信息。

被否决备选：① 让作答席 R4 也读口径库——等于把判据前置给被考者，判断题退化成抄规则，且会污染 pass^k 测量，**不做**；② 把用户裁决原文（含答案字母）直接喂给审查员——会泄题，改为"规则可见、答案不可见"。

## 二、库的结构

`audit/baseline/v2/caliber-library.json`（机读，唯一真源）+ `CALIBER-LIBRARY.md`（人读手册）。

| 类别 | 条目 | 来源 |
|---|---|---|
| 原则 principle | C-001 真实支出全额计入 / C-002 清单是待跟进不是已确认差错 / C-003 规律性口径差先计入并标注假设 / C-004 跨期歧义挂跟进不单边结案 / C-005 零值但字段有差异的条目保留 | ADJ 记录 round2/4/5-19（2026-10-20） |
| 例外 exception | E-001 内部系统缺字段且可工程化修复时先补字段、暂停统计 / E-002 有承接载体的归档表可接受 / E-003 转交能修复矛盾的责任方可接受 | 用户 2026-10-31 题级裁决（V2-12/21/24 场景） |
| 元规则 meta | M-001 例外 > 原则，引用须带 id+日期 / M-002 例外只在范围内成立 / M-003 多原则题的例外只解除 overrides 列出的条目，净冲突标 unresolved | 本轮试点实证 |

**三条设计约束**：
1. **反泄露**：库内只写规则与场景，不写任何题目的答案字母；检查器扫描 `用户裁[A-D]` 类模式，命中即库不合格。
2. **例外不得泛化**：每条例外必须声明 `overrides`（指向被覆盖的原则）与 `applies_to`（作用域），超范围仍按原则。
3. **库自己也有闸门**：`audit/kit/caliber_lib.py --check`（id 唯一、type 与 id 前缀一致、来源文件存在、overrides 指向 principle、precedence_rule 正确、反泄露扫描）；`--audit-review` 审计审查报告"每条口径结论是否带 id、例外是否写了范围"。

关键区分能力（试点实证，6 题）：
- **原则生效**：V2-11 判 `true_dispute`（B/D 同属"暂不计入"→ 合并后只剩一个立场，对应 C-003）；
- **例外命中**：V2-12 判 `exception`，明确"系统缺字段 + 可工程修复"才成立，且与 V2-11 形成对照（V2-11 缺的不是字段而是标注）；
- **双原则冲突**：V2-24 同时触发 C-002 与 C-005，试点判定"净结果仍冲突 → unresolved"，直接暴露库的结构缺口（见下）。

## 四、验证暴露的库缺陷（已修，非为通过而改）

1. **例外作用域过宽**：E-001 原只写"系统缺少口径字段"，未排除"外部方实务差异"——试点指出后者属 C-003 场景。已收紧为"内部可控系统缺字段 + 可工程化修复 + 补字段后差额可消除"。
2. **多原则题无规则**：E-002/E-003 原各只覆盖一条原则，而真实题会同时踩两条（V2-24）。已新增 M-003（例外只解除 overrides 列出的条目，净冲突标 unresolved），并依用户 V2-24 裁决把 E-003.overrides 扩为 `[C-002, C-005]`、作用域限定为"转交能修该矛盾的责任方"。

## 五、局限

- 试点仅 2 个会话、6 题、单模型（D-0035）；结论是"可举证性成立"，不是"审查质量已达标"。
- 未做端到端实验（R1/R2 带库 → R3 → R4 是否因此改答案）：R4 按设计不接库，故答案层不会变；本轮只解决"审查员能否举证"。
- 库的完备性依赖用户持续裁决；新裁决须按 §六 流程入库并重跑 `--check`。
