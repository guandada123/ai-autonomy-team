故逐项注入故障，观察是否变红。

## 三、E 项暴露的真实盲区（本次最大收获）

### 现象

注入 YAML 风格 `api_key: ⟨16位以上赋值⟩` 时，E 项**未报警**。

### 根因

原模式只认 JSON 风格（`"api_key": "…"`），不认 YAML/ENV 赋值风格。而真实泄露更常见于后者：

| 载体 | 样例 | 原状态 |
|---|---|---|
| JSON | `{"api_key": ⟨长字符串⟩}` | ✅ 覆盖 |
| YAML | `api_key: ⟨值⟩`（冒号赋值） | 🔴 **盲区** |
| ENV | `API_KEY=⟨值⟩`（等号赋值） | 🔴 **盲区** |
| 口令 | `password: ⟨值⟩` | 🔴 **盲区** |
| Bearer | `Authorization: Bearer …` | 🔴 **盲区** |

### 附带发现：模式有两份副本

`SECRET_PATTERNS` 同时存在于 `make_transfer.py` 与 `pre_release_check.py`——
**改一处另一处不知道**，违反单一真源。这也是两个文件都只认 JSON 风格的原因（都是早期复制）。

### 修复

1. 新建 `scripts/secret_patterns.py` 作为**单一真源**，覆盖 8 类模式（含上述四类新载体）；
2. `make_transfer.py` 与 `pre_release_check.py` 均改为 `from secret_patterns import …`；
3. 刻意**不匹配**单词 `token`——本项目文档大量讨论 LLM token 用量（`tokens: 126100`），
   只匹配带 `Bearer` 前缀的 Bearer token，避免把成本预算误报为凭据泄露。

### 修复后复测

| 注入 | 命中 | 标签 |
|---|---|---|
| `{"api_key": ⟨长字符串⟩}` | ✅ | api_key（JSON） |
| `api_key: ⟨值⟩` | ✅ | api_key 赋值（YAML/ENV/通用） |
| `API_KEY=⟨值⟩` | ✅ | api_key 赋值（YAML/ENV/通用） |
| `password: ⟨值⟩` | ✅ | 口令类赋值 |
| `Authorization: Bearer …` | ✅ | Bearer token |
| **反例**：`预算：tokens 126100/80000，token 合计 2.52M` | ✅ **不命中**（正确） | — |

## 四、B / C 的补测（原计划跳过，后补做）

初版验证曾把 B/C 标为「未测，理由：要让它红必须破坏判据或夹具，风险高」。
**这个理由不成立**——快照机制建立后，任何注入都可一键回滚，风险已被消除。

### 注入方式

把 `chk_decimal_equals` 的比较方向反转（`got == exp` → `got != exp`），
再 `--apply` 同步到包内。该判据同时被 `self-test` 与 `regress` 覆盖，故一次注入验证两项。

### 结果

| 项 | 输出 | 判定 |
|---|---|---|
| B 全量回归 | `43/50, EXIT=1` | 🔴 红（7 项失败） |
| C 判据自检 | `输出无法解析（EXIT≠0）` | 🔴 红 |

### 恢复

从快照 `cp` 回 `scripts/judges/verify.py` → `--apply` → 8/8 全绿。

### 顺带修掉 C 项的报错缺陷

初版 C 项在 self-test 输出格式改变时只打印「解析失败」，无法定位。
已改为附带 `EXIT` 码与末行输出（`输出无法解析（EXIT=非0，末行：…）`）。

### 附带发现：snapshot 的 label 未做路径安全处理

注入恢复时用 `--label "C项报错改进+B/C可证伪验证"`，其中的 `/` 被当成**路径分隔符**，
快照被创建为 `snapshots/<ts>-A+B/C/` 的**嵌套目录**，导致 `latest()` 取到父目录、
`_index.json` 读不到、H 项误报。

**已修**：新增 `safe_label()`，把非 `[字母/数字/中文/._+-]` 字符统一替换为 `_`。

> 教训：任何**会拼进路径的用户输入**都必须 sanitize。此处 label 本以为是"备注"，
> 实际成了路径片段——这类"看似无害的字符串"是路径穿越的常见入口。

## 七、附带发现：内容扫描类检测的「自指」通病

写本报告与配套脚本时，**同一份文档连续触发 5 次自指**——检测把自己的测试样例当成了违规内容：

| # | 触发方式 | 被哪项抓 | 处理 |
|---|---|---|---|
| 1 | 写出真实赋值形态的密钥样例 | E 密钥扫描 | 改为占位符 `⟨值⟩` |
| 2 | 写出一个形如真实编号的不存在编号 | F 决策编号 | 改为「形如 D-9xxx」 |
| 3 | 写出含待办触发词的句子 | G 待办扫描 | 改述 |
| 4 | **引用变量名**（该变量名本身含触发词） | G 待办扫描 | 改为「该项检查的正则定义」 |
| 5 | 用「尚＋未完成」描述「未完成」这一概念 | G 待办扫描 | 改为「尚未结束」 |

### 这不是巧合，是这类检测的固有局限

**内容扫描无法区分「违规内容」与「描述违规内容的文档」**。任何写出真实形态的技术文档都会自己抓自己。

### 两种处理方式，我选了后者

| 方案 | 评价 |
|---|---|
| 给文档加豁免白名单 | ❌ **不开这个后门**——一旦有白名单，写敏感信息只要起个"验证报告"的名字就能绕过 |
| 让文档不写真实形态（占位符/改述） | ✅ 采用。且对安全实践本身也更正确：**文档本来就不该包含可直接使用的凭据样例** |

### 可复用的规则

> 写验证报告/测试用例集时，样例必须是**不可执行/不可匹配的占位形态**，
> 包括：不写真实密钥格式、不写形如真实编号的字面值、不直接引用含触发词的标识符。

**同一错误在本项目已出现 6 次**（编号 2 次、审计报告 1 次、本报告 5 个子情形中的处理），
说明「写文档时想着检测」还没成为习惯。

## 八、回滚可用性演练

「备份存在」≠「回滚可用」——与「检测全绿 ≠ 检测有效」是同一个道理，故实演一次。

### 演练设计

选取 `scripts/inspect_agent_routing.py`（在 `build_package` 的同步映射内，可同时验证包内副本）。

| 步骤 | 操作 | 预期 | 实得 |
|---|---|---|---|
| 0 前置 | 核对快照副本与当前文件 sha256 | 一致 | ✅ 一致 |
| 1 模拟误删 | 删除该文件 | `--verify` 报「删除 1」 | ✅ `删除 1：scripts/inspect_agent_routing.py` |
| 2 从快照恢复 | `cp` 回快照副本 | `--verify` 一致 | ✅ `[PASS] 真源与快照完全一致` |
| 3 包内副本 | `build_package --apply` | 显示「未变」而非「写入」 | ✅ 包内 7779 字节，未触发重写 |
| 4 全量检查 | `pre_release_check` | 8/8 | ✅ 8/8 |

### 结论

回滚链路可用：**快照能存、能检出差异、能原样还原，且还原后包内副本不需重建**。

### 补充演练：另外三种回滚路径

初版只演练了「误删」，另三种仅标为未覆盖。后续补齐：

| 场景 | 演练方式 | 结果 |

| **A 误改回滚** | 给 `scripts/metrics.py` 追加一行废注释 | ✅ `--verify` 报「修改 1」→ 从快照 `cp` 回 → 一致；且 `metrics.py --self-test` 21/21 仍通过（证明恢复的是可运行版本，不是残文件） |
