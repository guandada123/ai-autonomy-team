# 存储可删性判据 —— 哪些能删、哪些删了就永久没了

> 写于 2026-10-27。**不是现在要清理**：系统盘可用 97 GB、外置 SSD 可用 1.6 TB，删任何东西都是自我安慰。
> 这份文件的用途只有一个：**将来空间真的紧时，不用重新验证一遍就能判断动哪里安全。**
> 所有数字均为「2026-10-27 实测」，会随时间变化；判据本身（下面每个 ⓘ 后面的验证命令）不会变。

---

## 一、核心结论：名字不能当判据

`_trash/` 这个名字让人以为是垃圾，`~/.Trash` 更是。实际相反：

| 位置 | 名字暗示 | 真实性质 |
|---|---|---|
| `_trash/snapshots-archive/` | 「垃圾」 | **193 个历史快照里，138 个 git 里没有 → 唯一副本** |
| `~/Backups/*.tar.gz` | 「备份」 | **是上面那批快照的唯一异地副本**（远端 git 不含 `_trash/`） |
| `~/.Trash/ai-autonomy-team-*` | 「已删」 | 这部分**确实冗余**（已验证） |

`.gitignore` 第 5 行原文已警告过：

> `#   · snapshots-archive/：被 prune 移出的历史快照 → **不可重建，只此一份**`
> `# ⚠️ 不要把整个 _trash/ 当成"可重建的垃圾"：删了归档，那 81 个历史时点就没了。`

2026-10-27 一次审计里，我按「看着像垃圾」判它可删，**验证后发现 138 个是唯一副本**。
所以本文件的第一条判据是：**先验证，再判断；不得凭目录名或 `.gitignore` 归类下结论。**

## 二、五块内容逐项定性

### ① `_trash/snapshots-archive/` — 🔴 不可删

- **是什么**：被 prune 从 `snapshots/` 移出的历史快照目录（每个含当时的真源文件副本）。
- **为什么不可删**：2026-10-27 实测 193 个目录，只有 55 个能在 git 历史中找到路径；
  其余 138 个（最早 2026-10-21）**从未入库** —— 2026-10-21 当天 git 提交数为 0。
- **ⓘ 复算**：
  ```bash
  python3 - <<'PY'
  import pathlib, subprocess
  arc = sorted(p.name for p in pathlib.Path("_trash/snapshots-archive").iterdir() if p.is_dir())
  out = subprocess.run(["git","log","--all","--name-only","--pretty=format:","--","snapshots/"],
                       capture_output=True, text=True).stdout
  seen = {l.split("/")[1] for l in out.splitlines() if l.startswith("snapshots/") and l.count("/")>=1}
  print(f"归档 {len(arc)}；git 有 {len([a for a in arc if a in seen])}；"
        f"git 没有 {len([a for a in arc if a not in seen])}")
  PY
  ```
  **判读**：第二个数字 < 第一个数字 ⇒ **有唯一副本，不可整体删除**。
  即使要删，也只能删「git 里有」的那部分，且删前逐个 `git cat-file -e` 确认。
- **唯一副本集中在早期**：2026-10-27 当天跑一次 snapshot 后归档从 193 增至 194，
  新移入的 `20261026-213016` 在 git 历史中有 2 次提交（可恢复）—— 说明近期归档多是入库过的，
  **风险集中在 10-21～10-23 那批提交不规律的时段**。若真要冒险删，也只能从最新的往里删，不能从最早的删。

### ② `~/Backups/ai-autonomy-team/*.tar.gz` — 🟡 旧的可删、最新必留

- **是什么**：`_trash/snapshots-archive/` 的打包副本。`make_backup.py` 存在的唯一理由就是
  「远端 git 不覆盖 `.gitignore` 的 `_trash/`」（见 D-0045），所以它是**归档的唯一外援**。
- **为什么旧的可删**：实测四份是**严格子集链** —— 最旧 ⊆ 次旧 ⊆ … ⊆ 最新，零独有文件。
  归档只增不减，所以新的必然包含旧的全部。
- **ⓘ 复算**（比文件名列表，不看大小）：
  ```bash
  cd ~/Backups/ai-autonomy-team
  for a in snapshots-archive-*.tar.gz; do echo "$a $(tar tzf $a | grep -vc '/$')"; done
  # 文件数应单调递增；再取最旧与最新比集合差
  comm -23 <(tar tzf 最旧.tar.gz | sort -u) <(tar tzf 最新.tar.gz | sort -u) | head
  # 输出为空 ⇒ 最旧是子集 ⇒ 可删
  ```
- **建议留 2 份**（最新 + 上一份），不是 1 份：它是唯一异地副本，单份损坏时要有第二个选择。

### ③ `~/Backups/ai-autonomy-team/*.bundle` — 🟢 可大量删（价值低但体积也小）

- **是什么**：git 完整历史的 bundle 快照（每份都是全量，`git bundle verify` 报 "complete history"）。
- **为什么可删**：HEAD 互为祖先链，最新一份含全部提交；且同样的历史远端的私有仓库也有一份。
- **ⓘ 复算**：`git merge-base --is-ancestor <旧HEAD> <新HEAD>` → 0 即祖先。
- **注意**：体积只有几 MB，删了省不出东西，**通常不值得动**。

### ④ `~/.Trash/ai-autonomy-team-*` / `snapshots-archive-*`（2026-10-23 那批） — 🟢 已确认冗余

- **是什么**：round34 手工删除时进废纸篓的一批旧备份（10-23）。
- **为什么可删**：2026-10-27 逐份验证 —— 6 个 bundle 的 HEAD 全部在本地 git 历史中；
  6 个 tar 的文件名集合全部被最新 tar 包含，零独有。**这是唯一一块真正纯冗余的项目数据。**
- **ⓘ 复算**：
  ```bash
  for b in ~/.Trash/ai-autonomy-team-20261023-*.bundle; do
    h=$(git bundle list-heads "$b" | awk '/refs\/heads\/main/{print substr($1,1,7)}')
    git merge-base --is-ancestor "$h" HEAD && echo "$b 冗余" || echo "$b ⚠️ 唯一"
  done
  ```
- **注意**：`~/.Trash` 里绝大部分**不是项目数据**（视频素材、微信 RSS 旧版、其他个人文件），
  那部分不在本判据范围内，清不清由用户自己定。

### ⑤ `~/.workbuddy/user-*/MEMORY.md.bak*` — 🔴 不建议删

- **是什么**：用户级记忆（**实际被注入的那份**）的写入前 / 定时备份。
- **为什么不能删**：这份文件**不在任何 git 仓库内**，这些 .bak 是它唯一的历史。
  一旦被覆盖写坏，没有第二次机会。
- **ⓘ 复算**：`ls ~/.workbuddy/user-*/MEMORY.md.bak* | wc -l`，与 `~/.workbuddy/MEMORY.md.bak*`
  （旧版冻结副本，可留 1 份）区分开 —— **两者对应的不是同一个文件**。
- **⚠️ 10-29 更正**：说".bak 是唯一历史"不精确——还有 14 份 `memory_snapshots`
  （`~/.workbuddy/memory_snapshots/`）。但**这三者全部位于外置盘 disk5s1**（软链），
  本无跨盘副本。现已新增 `~/Backups/ai-autonomy-team/memory-*.tar.gz`（**内置盘 disk3s5**，
  权限 600，逐份 sha256），由 `make_backup.py` 产出、与快照归档各自独立 retention。
  清理判断须覆盖这批新产物：它是 MEMORY 唯一的**跨物理盘**副本，比 .bak 更不能删。
  复算 `ls ~/Backups/ai-autonomy-team/memory-*.tar.gz | wc -l`。详见 D-0045 / L-0039。

## 三、什么情况下才需要动这份判据

| 触发条件 | 动作 |
|---|---|
| 外置 SSD 可用 < 100 GB，或系统盘可用 < 20 GB | 按 ②→④→③ 的顺序处理（先删已证冗余的，最后才碰归档） |
| 需要回退到某个历史快照 | 先查 ① 的复算，确认它在 `_trash` 还是在 tar 里，**不要先解压 tar** |
| 想改 `make_backup.py` 的保留策略 | 先读 ② 的复算，保留策略必须建立在「子集关系已验证」之上 |

**未达上述条件时：什么都不做。** 2026-10-27 实测删掉全部候选（约 256 MB）只让可用空间变动 0.01%，
而其中一项（①）判错的代价是永久丢失 138 个历史时点。

---

## 四、删除动作的三条硬规矩（沿用既有铁律）

1. **先验证，再复制，最后删源** —— 判据里的 ⓘ 命令必须真跑一遍，不看历史结论。
2. **删前用户确认**，逐项列出路径与体积；不打包成"清理一下"一句话就动手。
3. **走废纸篓，不走 `rm`** —— 本项目 round34 的删除就是这么做的，事后可恢复。

## 五、顺带记一条：全量备份没有保留策略

`make_backup.py` 每次生成**全量** tar（当前单份约 66 MB），工具本身不删旧份
（其输出明写「本工具不会删旧备份」）。按当前频率，一年会累积到数十 GB 量级。

这**不是现在的问题**（1.6 TB 可用），但如果哪天要加保留策略，注意两点：
- 保留判断必须建立在「子集关系已验证」之上，不能只按时间戳删；
- `snapshots-archive` 是只增的，所以「新的包含旧的」这个前提成立 ——
  但若将来引入"从归档中删除某些快照"的能力，该前提立刻失效，保留策略须重写。
