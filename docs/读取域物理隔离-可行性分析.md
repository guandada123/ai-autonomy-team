# 读取域物理隔离 · 可行性分析（清单第 8 项）

> 日期：2026-10-21 ｜ 目标机：Apple M4 / macOS 26.5.2
> 结论：**原方案在 LLM 席位架构下不可行；脚本层可用 sandbox 等效实现；建议改为逻辑审计兜底**

---

## 一、原要求（`目标机-人工确认清单.md` §8）

| 项 | 原文 |
|---|---|
| **背景** | 第 9 查只能检出**申报的**读取与**用作证据的**路径；未申报的读取对脚本完全不可见。Windows 上 `attrib +R` 与 ACL 都是软屏障，**不得视为安全边界** |
| **怎么做** | ① 建低权限运行用户；② 把 `fixtures/truth.json`、`fixtures/spec/`、`config/`、`judges/` 设为该用户不可读（`chmod 700` + 属主为运行者之外的用户）；③ **席位子进程以低权限用户运行** |
| **判据** | 以低权限用户执行 `cat fixtures/truth.json` → `Permission denied` |
| **诚实边界** | 做到了也只是**降低**风险 |

---

## 二、为什么原方案在这个项目里做不了

### 障碍 1（决定性）：席位不是本地进程

`migration-package/new_round.py:13` 原文：

> 子代理**只能由主会话通过 Agent 工具发起**。Python 脚本无法调用 Agent 工具。

`new_round.py:698` 补充：

> 本目录的 `prompts/` 是提示词文件，不是已发起的会话。

**含义**：席位（EX-01/02/03、PM-01、JD-01）是 **LLM 子代理**，其读取通过 Agent 工具的 Read/Grep 完成，
**不经过本地 shell 的文件权限检查**。

因此第 ③ 点「席位子进程以低权限用户运行」**没有可执行对象**——不存在那个进程。
`chmod` 与 `chown` 对 LLM 的文件读取**不起作用**。

### 障碍 2：照做会破坏现有工作流

第 ② 点要求把 `fixtures/truth.json`、`spec/`、`config/`、`judges/` 的属主改为「运行者之外的用户」并设 700。

后果：**当前用户（guan）立即失去读写权**，而 `verify.py`、`seat_check.py`、`regress.py` 全部需要读 `spec/` 与 `config/`。

→ 项目当场不可用。这不是「降低风险」，是「让系统停工」。

### 障碍 3：建系统用户是不可逆的高影响操作

`sysadminctl -addUser` 需管理员密码，创建后清理麻烦（残留用户账户）。
按项目既有原则，此类操作不应为一项 P2 检查而执行。

## 三、已验证可行的部分：本地命令的 sandbox 隔离

macOS 提供 `sandbox-exec`，可在**不修改文件权限**的前提下，对单个进程做文件读限制。

### 实测记录（2026-10-21，Apple M4 / macOS 26.5.2）

| # | 命令 | 结果 |
|---|---|---|
| 1 | `sandbox-exec -p '(version 1)(allow default)' /bin/cat <truth.json>` | ✅ 正常输出（对照组，证明文件本身可读） |
| 2 | `sandbox-exec -p '(version 1)(allow default)(deny file-read* (literal <truth.json>))' /bin/cat <truth.json>` | ✅ `Operation not permitted`，**EXIT=1** |
| 3 | `deny file-read* (subpath <spec/>)` → 读 `spec/arithmetic.json` | ✅ **EXIT=1** |
| 4 | 同一 sandbox 下 `ls <任务目录>` | ✅ 正常（**粒度可控**：目录可列、文件不可读） |

**与判据的差异**：原判据写「`Permission denied`」，实际报「`Operation not permitted`」。
两者都是拒绝访问，语义等价；差异源于 macOS sandbox 的错误码，非功能缺失。

### 能力边界

| 能隔离 | 不能隔离 |
|---|---|
| 本地 shell 命令（`cat`/`python3` 脚本） | **LLM 子代理的 Read/Grep**（不经本地进程） |
| 单次执行（无需改权限） | 持续生效（需每次包裹命令） |

## 四、结论与建议

### 结论

| 项 | 判定 |
|---|---|
| ① 建低权限用户 | ❌ 不做（高影响、不可逆、无实际收益——见障碍 1） |
| ② 改属主 + chmod 700 | ❌ 不做（会破坏工作流，见障碍 2） |
| ③ 席位子进程以低权限用户运行 | ❌ **架构上不存在该进程**（见障碍 1） |
| 脚本层 sandbox 隔离 | ✅ 已验证可行（§三） |

### 为什么不该强行「做到」

第 8 项的**目的**是「防止席位未申报地读取真值」。
但席位是 LLM，其读取行为只能通过**逻辑审计**（第 9 查：申报比对）来约束，
OS 层权限对它是**无效的**——即使把文件设成 700，LLM 仍可通过工具读取（工具进程有权限）。

**这是架构决定的事实，不是实现难度问题。**

### 建议（三选一，倾向 A）

| 方案 | 内容 | 评价 |
|---|---|---|
| **A 改为逻辑审计兜底** | 清单第 8 项标注「架构限制：席位为 LLM 子代理，OS 隔离无效；由第 9 查申报比对兜底」 | ✅ **推荐**。诚实反映现状，不做无效动作 |
| B 脚本层 sandbox | 为需要「模拟席位」的本地脚本（如未来的单 agent 对照实验）提供 `sandbox-exec` 包装 | 可选，当前无使用者 |
| C 位置隔离 | 把 `truth.json` 移出包，由裁判按需读取 | 改动大：影响 MANIFEST 与交付形态，且不解决 LLM 读取问题 |

### 诚实边界（沿用原文精神）

原文已写明「做到了也只是**降低**风险」。本分析进一步指出：

> 在 LLM 席位架构下，OS 层隔离连「降低」都做不到——它防的是本地进程，
> 而威胁来自 LLM 的工具调用。**真正的边界是「真值不进入席位可读的任何路径」这个设计约束本身**，
> 以及第 9 查对申报的比对。
