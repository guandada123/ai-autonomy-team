# L-0004 · 新规则不得与回归基线冲突——先问「这条规则要防的是什么」

- **日期**：2026-10-16
- **类型**：★ 升级候选（跨项目通用） 〔🔁auto-promote-2026-11-22·⏳待固化(容量不足)→「用例须被反证过才算覆盖」〕
- **发现方式**：自查（写协议文档时自己发现，不是跑出来的）

## 现象

修 F1 时给硬裁判加了一道「算术层路径白名单」闸门：凡比对型判据的 `path` 不在
7 个锚点白名单内，一律拒载（exit 2）。这条规则是对的 —— 它防止有人把**判断项**
塞进算术层冒充客观事实。

写 `docs/protocol/06-写入域与判据分层.md` 时，我顺手写下：

> 「若单层 spec 里出现白名单外的比对型 path → 同样拒绝加载。
> 理由：legacy 兼容的是**格式**，不是对判断项冒充算术锚点的纵容。」

**这句话会直接打穿回归第 2 项。**
legacy `truth.json` 里的 `summary.diff_count` / `diffs` / `summary.amount_diff_total` /
`summary.excluded_amount_total` **正是**白名单外的比对型判据 —— 一旦强制，legacy 立刻全部拒载，
而它是本项目唯一的回归基线。

## 根因

**规则的「正确性」和规则的「适用范围」是两件事，我把它当成了一件。**

白名单要防的是：**新写的判据**把判断项伪装成算术锚点。
它不该管的：**已经存在、已经逐条审阅过、其判断项已被识别并列入分层计划**的历史 spec。

对后者拒载，只会销毁回归基线，**不提高任何安全性** —— 零收益、纯损失。

## 处置

改为分层规则：

| spec 形态 | 白名单 | 行为 |
|---|---|---|
| 分层 spec 的 `arithmetic` 层 | **强制** | 越界即拒载 |
| 单层 legacy spec | **不强制** | 放行 + 标记 `carries_undeclared_judgment: true` |

并且把「不强制」的**代价**也如实写进协议：

> legacy 模式下硬裁判仍然只能复述判断 —— 兼容是为了不破坏历史，
> **不是为了继续用它做决策**。

## 教训（可复用）

1. **加规则时先跑一遍现有基线**，别等写完文档才发现冲突。
   「推理上明显正确」不等于「与既有资产不冲突」。
2. **问「这条规则要防的是什么」**，然后只防它。
   防御范围扩张到历史资产上，通常得到的是零收益 + 纯损失。
3. **豁免必须写明代价。** 只说「兼容旧格式」会让人以为旧格式仍然安全；
   必须同时写「兼容模式下它仍然有这个毛病，别拿它做决策」。

## 同源观察

本轮另有两次同类情形，均触发于「先跑一遍」而非推理：
- `regress.py` 初版未给 `verify.py` 传 `--out` → 拿不到摘要行 → 第 2/3 项**误判为 FAIL**；
- `regress.py` 的工作区根路径算错一级（脚本在 `scripts/` 下，上跳一级才对）。

> 三次都是**跑了才发现**。这与本项目既有铁律一致：
> 写盘必回读、变更先 dry-run、日志「成功」≠ 真的成功。
