# L-0029 评估外部工具：先对照**已量化的瓶颈**，别被"它省的成本"带着走

**日期**：2026-10-26
**标签**：工具选型 / 适用性评估 / 独立性
**状态**：已验证（一次 no-go 评估，见 D-0068）
**性质**：跨项目通用（任何"要不要引入这个新工具"的判断）★ 升级候选 〔🔁auto-promote-2026-11-22·✅已评估·同族覆盖→「外部工具先对照已量化瓶颈」〕

## 发生了什么

用户转来 Reason Network（跨机器/跨人的 agent 消息层，Rust daemon + P2P +
`list_team`/`send_message`/`ask_user` 三个 MCP 工具）。卖点是"省掉人在多机之间
搬消息的精力"。直觉上"听起来对本项目的多席位架构有用"。

## 对照瓶颈后，三条全部落空

| 它的卖点 | 本项目实况 |
|---|---|
| 省人工搬消息 | 席位由主 agent **单进程调度**，人工搬运成本 ≈ 0 —— 省一个不存在的成本 |
| 跨机器寻址 + 不可伪造批准 | 单人单机单仓库，无"别人的会话"可寻址 |
| 提高席位独立性 | **通信层不产生独立性**（独立性来自模型家族，本项目早已定案），它触及不到 |

## 教训

1. **"它能省什么"必须回答"我们现在真的在付这个成本吗"**。工具的价值 = 它消除的
   成本，而这个成本必须**实际存在**。自动化程度越高的系统，越容易被"省人力"类
   卖点误导——因为那部分人力早就没了。
2. **先看自己有没有该瓶颈的量化数据，再谈工具**。本项目有 κ（席间 0.855 / 臂内
   0.817，差 0.038）和定案"独立性来自模型家族而非 prompt"，所以一条外部消息层
   能不能提高独立性，**当场可判**，不必装了才知道。**没有量化瓶颈的项目，评估
   外部工具必然退化成"听起来不错"**。
3. **反向成本必须同样列出来**：新增常驻 daemon（本机 TCC 下访问外置卷会失败，
   本项目就在 `/Volumes/ZHITAI` 上）、可见性外扩（姓名/电脑/仓库/分支对队友可见）、
   新增一条更难归因的写入通道（昨天刚为"来源不明快照"加 caller 痕迹）。
   **不采纳的理由常常不在"它没用"，而在"它带来的新成本比它消除的成本更大"**。
4. **no-go 也要留复访条件**，且条件要可判定（有人参与 / 需跨机 / 需问活会话），
   避免日后变成"当时没采纳所以永远不 reconsider"。

## 复用方式

- 任何"要不要引入 X"的判断，先写一行：**本项目当前最痛的、已被量化的瓶颈是
  什么？** 若答不出量化数据，先去做量化，别选型。
- 卖点 → 成本映射表：左列"它声称省掉的"，右列"我们现在实际付的"，右列为 0 即
  否决（除非它同时解决了某个真正的瓶颈）。
