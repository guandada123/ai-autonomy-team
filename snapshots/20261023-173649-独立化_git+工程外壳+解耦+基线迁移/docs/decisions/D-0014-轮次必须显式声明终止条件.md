# D-0014 · 轮次必须显式声明终止条件

- **日期**：2026-10-20（补落为正式文件；实施早于此）
- **依据来源**：`scripts/new_round.py:690` 注释「AD-01 round6/7 第 3 查实测缺口」
- **操作分级**：🟡 中（新增 manifest 必填段，影响所有新建轮次）
- **状态**：已执行

## 决策

`round-manifest.json` 必须显式声明 `termination` 段：终止条件、声明人、说明。

`evidence_round` 的预期终态是**判断层 pending（等人签字）**，不算「未完成」；
`revision_round` 的终止条件是 `rounds_exhausted`。

## 依据

| # | 依据 | 来源 |
|---|---|---|
| 1 | 第 3 查在 round6/round7 实测到缺口：轮次没有声明何时算「结束」，导致「pending 等人签字」与「任务没跑完」不可区分 | AD-01 第 3 查实测 |
| 2 | 实现落在 `make_manifest()`：role 为 evidence_round 时 `condition=pending_adjudication`，否则 `rounds_exhausted` | `scripts/new_round.py` `termination` 段 |
| 3 | 四选一终止条件在协议中有定义 | `protocol/02` §4.2 |

## 备选方案与未采用理由

| 备选 | 未采用理由 |
|---|---|
| 靠轮次目录存在与否推断终态 | 目录存在只说明开过轮，不说明跑到哪一步 |
| 用 verdict 文件作为终止标志 | 无 verdict 的轮次（如闸门拦截轮 r8–r10）会被判为「未终止」，与实际不符（见 `adjudication_not_required` 标注） |

## 审计发现

「pending」在多数流程里是中间态、异常态，但**在本项目的 evidence_round 中它是预期终态**。
若不显式声明，后续任何「检查轮次是否完成」的脚本都会把等人签字的轮次误判为卡住。

## 落地校验

| 校验 | 方法 | 期望 |
|---|---|---|
| 新轮次含 termination | `new_round.py` 建轮后读 manifest | 含 `termination.condition` |
| evidence_round 终态 | 建 evidence 轮 | `condition == "pending_adjudication"` |
