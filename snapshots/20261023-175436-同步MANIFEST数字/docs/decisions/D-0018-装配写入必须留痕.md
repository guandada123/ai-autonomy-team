# D-0018 · 装配写入必须留痕（assembly-log.jsonl）

- **日期**：2026-10-20（补落为正式文件；实施早于此）
- **依据来源**：`scripts/build_package.py:152` 注释「round11 AD-01 第 8 查实测缺口」
- **操作分级**：🟡 中（新增落盘日志）
- **状态**：已执行

## 决策

`build_package.py --apply` 的每次写入必须落盘到 `migration-package/assembly-log.jsonl`，
记录 `ts` / `actor` / `written` / `unchanged` / `changed_files`。

## 依据

| # | 依据 | 来源 |
|---|---|---|
| 1 | **包内 mtime 刷新与席位越权写入在元数据上不可区分** —— 第 8 查无法判定「161 个 fixtures 文件是谁写的」 | AD-01 第 8 查实测缺口（round11） |
| 2 | 装配日志把「发起方 = 编排方装配脚本」落盘后，写入域检查与结构审计才能区分**合法装配**与**越权写入** | `scripts/build_package.py` 日志段 |
| 3 | 该日志同时也解释了「包内文件为什么被改回原样」—— 见 D-0022 的历史事故 | [`D-0022`](./D-0022-包内路径铁律.md) |

## 备选方案与未采用理由

| 备选 | 未采用理由 |
|---|---|
| 靠文件 mtime 判断来源 | 装配与越权都会刷新 mtime，不可区分（本决策要解决的正是一点） |
| 装配时把文件标记为只读 | 会打断正常构建流程，且只读可被绕过 |

## 审计发现

**「能写」与「被允许写」是两件事**：包内文件技术上谁都能改，但没有发起方记录时，
审计只能看到结果、看不到来源。日志把「谁发起」变成可查的事实。

## 落地校验

| 校验 | 方法 | 期望 |
|---|---|---|
| 日志存在 | `wc -l migration-package/assembly-log.jsonl` | 随 `--apply` 次数增长 |
| actor 字段 | 读最后一条 | `"build_package.py(--apply)"` |
