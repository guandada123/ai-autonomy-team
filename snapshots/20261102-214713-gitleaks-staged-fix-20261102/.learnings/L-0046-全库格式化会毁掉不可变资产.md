# L-0046 全库格式化会毁掉三类"不可变资产"——exclude 不是优化，是正确性要求

**日期**：2026-11-02
**标签**：格式化 / 不可变资产 / 快照 / 冻结哈希 / 外部素材 / pre-commit
**类型**：跨项目通用
**性质**：任何"对全库跑格式化/自动修复/批量重写"的场景（ruff format、prettier、gofmt、sed 批量替换）
**状态**：已实测（本日启用 pre-commit 首跑，443 个文件被改，其中 331 个属误改）

## 现象

首次 `pre-commit run --all-files`，12 个钩子里 4 个"会改文件"，结果改了 **443 个文件**。
看着像"统一格式"，实际踩了三类不可变资产：

| 被改的 | 数量 | 为什么这是破坏 |
|---|---|---|
| `snapshots/` | 108 | 历史快照的全部意义是"某一时刻的原文"，改了就不是那个时刻了 |
| `migration-package/` | 223 | 自动生成产物，下次 build 会被覆盖；改了等于白忙 + 制造噪音 |
| `docs/templates/audit-kit/`、`ci-snippets/` | 1+ | 从别的仓库按 commit 取的**字节级副本**，改了就无法再用哈希证明"是原件" |
| `audit/baseline/judge_baseline.py` | 1 | 被 `frozen-v1.json` 的 sha256 锚住（题库冻结），改它 = 换试卷，此前所有分数作废 |

最后一条是被**回归第 53 项当场抓到的**（"题库 v1 未漂移"逐个比对 5 个冻结文件的 sha256）。

## 判据

全库批量改写前，先问三句：

1. **这批文件里有没有"历史存档"？** —— 快照、备份、归档、`_trash`。
   它们的值不在"格式正确"，而在"与当时逐字节相同"。
2. **有没有"哈希被别处引用"的文件？** —— 冻结清单、素材清单、发布指纹。
   批量改写必然改内容，而这类校验判的就是内容哈希，两者天然冲突（不是 bug，是定义）。
3. **有没有"从外部按 commit 取的副本"？** —— 素材、vendor 目录、第三方快照。
   它们的可信度全押在"与源逐字节相同"上，改一个空格就失去这个性质。

三问命中任一 → 必须写 exclude，并且**把 exclude 的理由写进配置注释**，
否则下一个人会以为是多余的、顺手删掉。

## 做法（本次）

在 `.pre-commit-config.yaml` 顶层加：

```yaml
exclude: ^(snapshots/|migration-package/|outputs/|_trash/|docs/templates/audit-kit/|docs/templates/ci-snippets/|audit/baseline/judge_baseline\.py$)
```

并在注释里写明：以后往 `frozen-v1.json` 加冻结文件，**必须同步加进这个正则**。

## 边界（别过度排除）

- 不要因为"怕改坏"就把整个源码目录排掉——格式化源码正是它的价值。
- 排除面每多一条，检出/统一的效果就少一块。本次只排第 2 节三问命中的类别。
- 结构化产物（如 `migration-package/`）若确实需要统一格式，
  应该改**生成器**让它生成时就规范，而不是生成后再格式化（否则下次 build 又还原）。

## 与既有铁律的关系

同源于「同一事实只允许一处自由」「声明是副本，副本必须机器核对」：
格式化是"批量改写内容"，而内容哈希是"证明内容没变"——
**任何批量改写都必须先枚举"谁在用哈希证明什么"**，否则改完就是静默毁证。
