# L-0015 · 把本地门禁搬进 CI 时，先对齐环境的默认值

日期：2026-10-23 ｜ 出处：D-0046 首次 CI 运行 ｜ 关联：`D-0046`、`L-0009`

## 现象

`make selftest` 在本机连跑多次全绿；同一份代码、同一个 commit，在 GitHub Actions
上 **11 秒就红**，失败在备份自检的第 1 项：

```
FAIL 完好的 bundle 应通过
[FAIL] 备份验证逻辑自检：3/4 项
```

本地同一个脚本：4/4。

## 根因

`actions/checkout` 默认 `fetch-depth: 1`（浅克隆）。而 `make_backup.py` 的自检里
「完好的 bundle」这一例是**拿当前仓库本身**去 `git bundle create --all`。

浅仓库里这个命令**会成功返回**，但产出的 bundle 缺历史边界对象，**clone 不回来**——
于是「好的 bundle 应该通过」这一例按定义失败。

判定不是靠猜：本地 `git clone --depth 1` 后跑同一条命令，输出与 CI 逐字相同。
所以这不是「Linux 与 macOS 的差异」，是**检出方式的默认值差异**。

## 为什么危险

这条失败当时看起来像「CI 环境问题」，很容易被归因成噪音，然后：
给自检加 `if CI: skip`，或者把备份自检从 CI 里摘掉 —— 两种做法都在**降低门禁强度
去迁就一个环境默认值**，而真正的结论是「浅克隆不能当备份源」。

反方向同样危险：如果这例恰好**假绿**（比如检查项只是 `rc == 0`），CI 会长期通过，
而人以为「CI 已经验证过备份可用」。

## 修法

两处一起改，缺一处都会留后患：

1. **CI 对齐默认值**：`fetch-depth: 0`。门禁要验的是完整仓库，就给完整仓库；
2. **工具拒绝不可能的输入**：`make_backup.py` 前置检查 `git rev-parse --is-shallow-repository`，
   浅克隆直接 rc=2 并给出 `git fetch --unshallow`。原来的表现是下游「clone 失败」，
   看不出原因。

## 通用化

本地 → CI 有四个默认值差异，搬门禁时逐条对齐：

| 差异 | 本地常见 | CI 默认 | 后果 |
|---|---|---|---|
| 历史深度 | 完整 | **`--depth 1`** | 依赖历史的检查假红或假绿 |
| locale | UTF-8 | 可能是 C/POSIX | 中文路径与编码比较 |
| Python 版本 | 3.13 | 3.12 | 语法/行为差异（本项目只承诺 ≥3.9） |
| 文件系统大小写 | macOS 不敏感 | Linux 敏感 | 只差大小写的路径在本地永远不报错 |

**通则：本地绿是「这台机器上绿」，不是「这个 commit 绿」。**
搬运门禁不是复制命令，是复制**前提**——前提没写下来的，CI 会替你说出来，代价是一次红的推送。
