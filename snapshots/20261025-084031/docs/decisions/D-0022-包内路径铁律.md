# D-0022 · 包内路径铁律：脚本皆构建副本，夹具是包内独有源

- **日期**：2026-10-20（初版语境）；2026-10-20 补落为正式决策文件
- **决策者**：PM-01 / 用户
- **操作分级**：🔴 高（约束一切对 `migration-package/` 的修改路径）
- **状态**：已执行（并由 `build_package.py` 的映射表强制）

## 决策

`migration-package/` 内的一切**分两类**，修改路径完全不同：

| 类别 | 包含 | 修改方式 |
|---|---|---|
| **构建产物 / 副本** | `judges/**`、`protocol/**`、`prompts/**`、包根 3 个脚本（`make_fixtures.py` / `inspect_agent_routing.py` / `new_round.py` / `metrics.py`） | **必须改 `scripts/` 真源**，再 `build_package.py --apply` 同步。直接改包内副本会被下次构建覆盖 |
| **包内独有源** | `README.md`、`precheck.py`、`gen_manifest.py`、`MANIFEST.json`、`config/**`、`fixtures/**`、`runs/**`、`docs/**` | **直接改包内**。这些**没有**源侧副本，也不该有 |

### 表述修正（本次落定的关键改动）

初版表述为「包内不含任何脚本」——**与事实不符**：包内实含 `gen_manifest.py`、`make_fixtures.py`、`metrics.py`、`new_round.py`、`inspect_agent_routing.py`、`judges/`。

**正确表述**：

> 包内脚本**均为构建副本或包内独有源，没有第三个类别**。构建副本的真源在 `scripts/`，对它们的任何修改必须在 `scripts/` 同步，否则下次 `--apply` 即丢失。

## 备选方案与未采用理由

| 备选 | 未采用理由 |
|---|---|
| 把包内脚本也纳入同步管辖 | 会触发 MANIFEST 重建与多处路径引用改写，收益小于代价（原注释已评估） |
| 把 `fixtures/**` 搬到 `scripts/` 下当真源 | 同上；且 `regress.py` 在包内运行需要 `fixtures/` 就地存在 |
| 取消包内副本、包只依赖 `scripts/` | 包要能独立交付给外部，不能依赖团队根目录结构 |

## 审计发现

1. **「不含任何脚本」是不准确的表述，会误导操作**：读者会以为包内所有脚本都可随意改，实际其中 9 个会被覆盖、其余是独有源。本次已改为分类表述。
2. **`fixtures/**` 是包内独有源，但它由生成器产出**——这是本铁律唯一的例外情形：文件位置在包内、内容却来自 `scripts/make_tasks_20.py`。因此对夹具的修改**必须改生成器**，改了包内文件也会被 `regress.py:853` 覆盖。这条比「包内独有源直接改」更严格，是本次事故换来的。
3. **同一铁律下的三级修改路径**：

```
改 judges/** 等构建副本  → 改 scripts/ 真源 → build_package.py --apply
改 fixtures/tasks/**     → 改 scripts/make_tasks_20.py → 重新生成
改 config/params.json    → 直接改包内（无生成器，无源侧副本）
```

判断依据：**看该文件有没有生成器**。有生成器就必须改生成器，没生成器才能直接改。
