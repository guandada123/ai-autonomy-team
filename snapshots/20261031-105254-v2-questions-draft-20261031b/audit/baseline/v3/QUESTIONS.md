# Q01 · 快照保留份数

## 情形
`make snapshot` 每次把文档与源码打一份快照入 `snapshots/<时间戳>/`，超出保留数的**移动**到 `_trash/snapshots-archive/`（不删除）。当前保留 **3 份**，合计 3.7MB。今天打快照时轮换了 1 份。

## 事实
- 门禁 H 项只比对**最近 1 份**快照，另外 2 份是历史回看用。
- 归档目录在 `_trash/` 下，不入库，但文件还在本地磁盘。
- 仓库另有 git 全量历史 + 私有远端完整副本 + 独立 bundle/tar 备份。
- 保留数可调（`--prune-keep N`），下限是 1（再低会让 H 项失去比对基准）。
- 单份快照约 1.2MB，增长主要随文档数量走。

## 选项（选一个）
- `A` 保持 3 份
- `B` 改成 5 份
- `C` 改成 2 份

# Q03 · 36 条校准集由谁标注

## 情形

- 你自己标：能拿到真正独立的判据，但 36 条逐条判定要花时间，且需要你给出判定标准。
- 现状：结论已按「仅一致性检查」的措辞降级写入 D-0052。

## 选项（选一个）
- `A` 你自己标注 36 条
- `B` 换另一个模型标，与现有标注做交叉比对
- `C` 维持自标自测，结论永久限定为「一致性检查」

# Q10 · v2 判分器要不要推广到其它项目

## 情形
`score_v2.py` 现在只服务本仓 v2 题库。Claw / QTS / StockInsight 各有自己的判据与门禁，没有同类判分器。

## 事实
- 判分器依赖每题的 `key_reasons` 关键词表，与具体题集强绑定。
- 指标（一致率 / 平衡准确率 / 理由覆盖 / 危险失误）与题集无关，可复用。
- 推广需要：各项目自己出题、自己裁决、维护自己的关键词表 —— 即三份新的出题与裁决工作量。
- 本仓已有教训：跨项目共享的前提是「谁改、怎么引、怎么同步」都有答案（见 Q06）。

## 选项（选一个）
- `A` 推广到其它项目（各自出题）
- `B` 不推广，只在本仓用
- `C` 先把判分逻辑抽成通用脚本（题集格式解耦），再决定是否推广
