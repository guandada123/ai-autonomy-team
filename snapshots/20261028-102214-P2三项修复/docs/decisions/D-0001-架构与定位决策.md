# D-0001 · 项目定位、架构落地与技术路线

- **日期**：2026-10-16
- **决策者**：PM-01（主会话）
- **操作分级**：🟢 低（全部为新增文件，无覆盖、无外部写入）
- **状态**：已执行

## 决策

1. 项目定位：**本机（Windows）= 验证机，Mac mini M4 = 落地机**；可迁移性升为一等需求。
2. 硬裁判**只用 Python 标准库**实现，保证在 macOS 系统 `python3` 上零依赖运行。
3. **本轮不创建任何定时自动化任务**，改为导出 `config/automations.json` 定义文件，由用户在 M4 上重建。
4. 跨家族路由**先实测再定架构**（已实测，结论：可用，无需降级）。
5. 试跑载体采用**合成数据任务**，不碰真实业务数据。

## 备选方案与未采用理由

| 备选 | 未采用理由 |
|---|---|
| 硬裁判用 openpyxl / python-docx 实现 | M4 上没有这些库（依据 2/3），硬裁判将无法在目标机运行——而它是**唯一有否决权的部件** |
| 硬裁判改用 Node 实现 | 引入第二套运行时；M4 的 Node 版本未确认；且跨平台面更大 |
| 直接创建定时自动化任务 | 写 `workbuddy.db` 是全局、跨项目、**不可逆**操作（依据 4）；且目标机是 Mac，本机建的任务在 M4 上无意义 |
| 整体拷贝 `workbuddy.db` 迁移 | 全局库、含密钥、含两平台不通用状态 |
| 假定跨家族可用、跳过实测 | 软裁判是双裁判架构的一半；假定错了整个后续验证白做。实测成本极低（两次短调用） |
| 用真实业务数据试跑 | 不可逆、涉隐私；用户已选合成任务 |
| 用纯文本生成任务作为试跑载体 | 难以构造客观硬裁判，无法验证「证据制优于投票制」这一核心命题 |

## 审计发现

1. `scripts/inspect_agent_routing.py` 首跑失败：脚本按「项目目录」层级解析，实际传入的是「会话目录」。已修正为兼容两种层级（`<proj>/<session>/subagents/` 与 `<session>/subagents/`）。**这是一个真实的路径假设错误，不是环境问题**——说明「先跑一遍再声称可用」是必要的。
2. 探针 A 自述模型为「GLM-5.1」且恰好正确，但**该自述不构成证据**（模型未必知道自己被路由到哪）。已确立纪律：路由核验必须读运行时 `providerData` 记录。
