# L-0047 「Passed」不等于「在工作」——钩子空转时，日志和正常几乎一样

**日期**：2026-11-02
**标签**：钩子 / 闸门 / 假绿灯 / 可证伪 / pre-commit / CI
**类型**：跨项目通用
**性质**：任何"装了自动检查就以为有保护"的场景（pre-commit、GitHub Actions、lint 步骤、gitleaks、审计脚本）
**状态**：已实测（12 个 pre-commit 钩子逐个用负样本打，**2 个在空转**，且从日志完全看不出）

## 现象

12 个钩子装好、`--all-files` 全 Passed、CI 全绿。看上去保护齐备。
直到有人主动造了一个含假密钥的文件去提交——**它被顺利提交进去了**。

查下来：该钩子（`gitleaks git --pre-commit`）扫的是**工作树 diff**，
而 commit 时所有改动都已进暂存区、工作树无差异 → 日志写
`0 commits scanned / scanned ~0 bytes` → 无泄露 → 退出码 0 → **Passed**。

它不是报错，是**安静的空转**。而空转在日志上与"检查了、没问题"长得一模一样。

## 两类高风险的钩子（必须单独验证）

### ① 不走文件分发路径的

`always_run: true` + `pass_filenames: false` —— 钩子不接收文件列表，自己找目标。
pre-commit 不会告诉它"该检查哪些文件"，它找错了也没人知道。

本仓实测：gitleaks（空转）、check-merge-conflict（空转）都属此类风险面。

### ② 行为依赖外部状态的

- `check-merge-conflict`（pre-commit-hooks v4+）：**默认只在 git merge 状态才检查**，
  非 merge 直接 return 0。日常提交永远不在 merge 状态 → 恒真通过。
  修法：加 `--assume-in-merge`。实测同一文件：默认 exit=0 零输出；加参数后报 3 处 exit=1。
- 其他同类：依赖"有 diff / 暂存区非空 / 当前分支是 main / 环境变量存在"的钩子。

## 判据

装完自动检查后，**必须做一次负样本击破**，且必须走**真实执行路径**：

| 检查项 | 做法 |
|---|---|
| 造一个**应该被拦**的样本 | 假密钥 / 语法错 / 冲突标记 / 超大文件 / 格式错 |
| 走真实路径 | pre-commit 用 `git add` + `git commit`；CI 用真 push |
| 确认**被拦** | 退出码非 0 **且** 看日志确认是**目标钩子**拦的 |
| 确认样本没落地 | `git log` 没多提交、文件没入库 |

## 一个必须避开的测试陷阱

对**未跟踪文件**跑 `pre-commit run --files <f>`，fix 类钩子会改文件却报 Passed——
因为 pre-commit 的"文件是否被修改"检测依赖 git diff，看不见未跟踪文件。
同样内容走 `git add` + `git commit` 就正确报 Failed。

我第一次验证 ruff-format 时就是这个坑，误判它空转；换成 commit 场景重测才确认它正常。
**验证"会不会拦"必须走真实 commit，不能用 run --files 对未跟踪文件测。**

## 边界（别过度怀疑）

不必给每个钩子都写负样本——成本过高。优先级：

1. 安全类（密钥、私钥）→ **必测**，失效代价最大
2. 不可逆类（大文件、删除保护）→ 必测
3. 格式/风格类 → 抽查即可，失效代价低（最多格式不统一）
