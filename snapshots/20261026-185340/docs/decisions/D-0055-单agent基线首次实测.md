- **决策者**：用户（"开始"——接上一轮"要我先测基线吗"）
- **操作分级**：🟢 低（只新增测量产物与记录；不改判据代码）
- **状态**：生效

## 决定

在留出任务集上完成**首次单 agent 基线实测**，产物落在 `audit/baseline/`：
`single-agent-answers-20261024.json`（作答）、`ground-truth-20261024.json`（真值）、
`judge_baseline.py`（判分）、`RESULT-20261024.md`（结论）。

**测量顺序是关键**：先封存盲答，再去量真值——反过来就是看着答案写答案。

## 结果

| 指标 | 数值 |
|---|---|
| 任务数 / 有效样本 | 10 题 / **n=9**（T01 因题面口径未声明被排除） |
| 通过 | 9 / 9，通过率 **1.000** |
| 点估计 | 100% |
| **单侧 95% 下界** | **71.7%**（`0.05^(1/9)`） |

首次判分其实是 **7/9**——差额不在作答，在判分脚本：它只接受 list，
而 T06/T07 我用 dict 作答，数值完全正确也被判错。已修（两种容器都接受），
**两次分数都记录在案，不藏第一次**。这正是本项目反复强调的那类缺陷：
判据自身的格式假设会造成假失败。

## 关键结论：卡点不是多席位样本量，是参照太抖

| 单 agent n | 全对时下界 | 多席位所需 n（margin 5pp） |
|---|---|---|
| 9（本次） | 71.7% | 8 |
| 20 | 86.1% | 15 |
| 30 | 90.5% | 20 |
| 40 | 92.8% | 23 |

本次基线自身不确定度约 **±28pp**，是 margin（5pp）的 **5.6 倍**。于是：

- 按点估计 100% 代入 → 多席位需 n≥59（成本不可接受）；
- 按下界 71.7% 代入 → 多席位需 n≥8，但此时"非劣效 5pp"几乎没有约束力（判据空转）。

**两条路都不可取**，说明 V2 现在仍不可评，且原因不是"多席位要跑多少"，
而是**参照自己样本量不够**。要把参照稳到下界 ≥90%：单 agent 需 **n≥30 且全对**，
再多席位 n≥20，合计约 50 个任务。

## 顺带发现：一个真实的口径不一致

T01 问"备份归档里有多少个文件"：`make backup` 自己报 **9,197 个文件**，
而 `tar -tzf | wc -l` 数出 **10,024 个条目**（含 827 个目录）。
同一件事两个口径，差 8.6%，此前无人注意——**包括备份工具自己的输出与还原验证**。
本题因题面未声明口径被判"排除"，但差异本身记入真值文件。

**待修（2026-10-24 01:05 已修）**：`make_backup.py` 现已同时给出两个口径——
`tar_counts()` 独立成函数并报「N 个文件 / M 个条目（含 K 个目录）」，自检增至 5/5，
新增一条用例把「目录不算文件」钉住（`tar_counts(fake) == (1, 2, 1)`）。
真备份实测：2348 = 9,197 文件 / 10,024 条目 / 827 目录，两个口径可对上。

## 明确不做

- ❌ **不把本次 100% 当作"单 agent 足够好"的证据**：n=9、题目由我出、答案在本会话内已知，
  它测的是"已知事实的回忆与换算"这一类任务的上界，不是通用能力；

- ❌ **不扩到 200+ 题**：见下，先把 30 题跑稳再说。
