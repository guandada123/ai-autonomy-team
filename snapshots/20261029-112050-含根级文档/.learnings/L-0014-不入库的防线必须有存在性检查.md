# L-0014 · 不入库的防线，必须有「存在性检查」替它站岗

日期：2026-10-23 ｜ 出处：D-0045 遗留项收口 ｜ 关联：`D-0045`、`L-0009`、`L-0012`

## 现象

`D-0045` 把「推前扫密钥 + 核对远端是否 private」绑成了 git 钩子（`make hooks` 写
`.git/hooks/pre-push`）。钩子本身**不入库**——这是 git 的设计，不是疏漏。

于是同一条防线有两种状态，而**输出完全一样**：

| 状态 | 人看到的现象 |
|---|---|
| 钩子已装 | `git push` 正常；有泄漏时被拒 |
| 钩子没装（换机 / 重建 clone） | `git push` 也正常 |

没有钩子时推送照样成功，**没有任何提示说"拦截层不在"**。防线不是坏了，
是**根本不存在**，而它不存在这件事不可观测——直到真的推了密钥上去。

2026-10-23 复查发现：`verify_handover.py` 5 项里没有任何一项看钩子；
`make pre-push` 只在人记得跑时才有用。用户在同一天的交接提醒里点名了这件事：

> `make hooks` 是本地文件、不入库，换机或者重建 clone 后第一件事是重装钩子，
> 否则推送闸门等于不存在。

## 为什么容易漏

钩子是「环境状态」，不是「代码状态」。代码状态由测试覆盖，环境状态**没有任何测试看它**——
除非有人专门写一条。这类东西的共同特征：

- 它由某条命令安装，装完就忘；
- 缺失时系统**不报错**，只是少了一层保护（fail-open）；
- 恰好只在「最需要它的场景」（新机器、急着推）缺。

同族缺陷：`.env` 没配 → 功能静默降级；`core.hooksPath` 指错 → 钩子永不触发；
备份盘没挂载 → 「找不到就换个地方找」。**都是 fail-open。**

## 修法

把存在性做成**接手验收的失败项**，而不是写在文档里提醒：

- 第 6 项查三件事：`git rev-parse --git-path hooks/pre-push` 找得到、可执行、
  内容调的是本仓 `scripts/pre_push_scan.py`（装了别的钩子不算）；
- 走 `git rev-parse --git-path` 而不是硬编码 `.git/hooks/`——设了 `core.hooksPath`
  的机器上，硬编码会给出**假绿**；
- 缺了就 FAIL 并打印修复命令（`make hooks`），不打印"建议检查"。

`make handover` 是接手新机器的第一条命令，把检查放这里 = 让「第一次运行」就暴露它。
代价是全新 clone 首跑必然红在第 6 项——**这个红是真话，不是误报**。

## 通用化

| 防线的载体 | 会不会跟着仓库走 | 需要的补偿机制 |
|---|---|---|
| 代码、判据、夹具 | 会 | 测试即可 |
| **git 钩子、本地配置、cron、大盘挂载** | **不会** | **必须在某条"人一定会跑"的命令里做存在性检查** |
| 人的记忆 | 不会 | 等同于没有 |

**通则：凡 fail-open 的防线，都要有一条 fail-closed 的检查看着它。**
判断标准很简单——「这条防线消失时，谁会红？」答案是「没人红」的，就还没做完。
