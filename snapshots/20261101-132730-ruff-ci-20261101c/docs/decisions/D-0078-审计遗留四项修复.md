## 二、`inspect_status` 的当前态口径（这是唯一会每天误报的项）

**病**：`verdict-layered.json` / `pending-adjudication.json` 是 `verify.py` **判据侧**产物，
`verdict=pending_adjudication` 的语义是「当时有 N 项等人签字」（协议 05 §3：未裁决≠失败）。
裁决落盘后当前态在 `answer-status.json`，而旧产物**按设计不回写**。
脚本只打 verdict 行 ⇒ 已裁决的轮次读起来全是「未裁决」。

**关键发现：这不是 round13 的特例。实测 29 轮同形**（round2–7、11–33）。
先前把它当"round13 显示问题"处理（只加 `display_caveat` + 改 08:05 prompt），
特例化会留下 28 个同形隐患 —— 已改为修判据。

**修**：
- 新增 `current state:` 行，**唯一真源 = `answer-status.json`**；两套版式都认
  （verify.py 的 `adjudication_state` / round34 的 `status: resolved_by_human`），
  且**标明是哪套** —— 否则「没有文件」和「字段名不同」会混成同一个「未终态」
  （round34 差点被误报成无 answer-status，实测拦下）。
- verdict 行加 `（判据侧快照 @ts）`；与当前态冲突时追加 `← 已被 … 取代（勿据此人判未裁决）`。
- 新增 `CURRENT STATE SUMMARY` 段：已 resolved 30 轮 / 未终态 4 轮（1、8、9、10）/ 自称 pending 但已裁决 29 轮。
- 新增 `--runs DIR`（默认行为不变）+ 参数错误 exit 2。原文档自称"退出码恒 0"，
  加了参数就必须有参数错误，否则「路径写错」会静默变成「0 轮、一切正常」。

**可证伪**：回归第 55 项用**三个合成轮**（已裁决+verdict 自称 pending / 无 answer-status /
非 verify.py 版式）按轮切段断言。不依赖活数据 —— 活数据的分布会变，靠它续命的判据不算判据。
若把 `current_state` 改回「优先读 verdict」，roundA 立刻红；若写成"只认 `adjudication_state`"，
roundC 红（这正是我第一版的 bug）。守门项随之 55 → 56（沿用 D-0057 顺延先例）。

## 三、备份保留策略：有策略 ≠ 有删除权

**事实**：16 份 / 510MB，其中 8 份 bundle 仅 23MB，8 份 tar 约 489MB（36→74MB 递增，逐份近乎全量重复）。
工具自述"不删旧备份"，于是"无策略"被默认成"无限增长"——一夜新增 2 份，增长速率由人的记忆决定。

**策略**（写进脚本 docstring，可执行）：

| 产物 | 保留 |
|---|---|
| `*.bundle` | 全留（3MB/份，代码历史唯一可还原副本；删它省不出空间却削掉回滚深度） |
| `snapshots-archive-*.tar.gz` | 最近 3 份 + 每月最后一份（月度锚点） |
| `memory-*.tar.gz`（2026-10-29 补） | 最近 3 份 + 每月最后一份（月度锚点），**与上一行各自独立**计算，不共用"最近 3"预算（体量/频率/用途不同，混算会互相挤占） |

**执行方式**：`--retention` 只出分类报告（当前：保留 11 份 / 244.3MB，可清理 5 份 / 266.1MB），
并给出「先复核、再执行」的两条命令。**脚本不删、不移动任何文件。**

**弃因**：目标目录在 `~/Backups/`（个人目录），删备份不可逆；且"哪一份还能扔"取决于恢复场景
（要不要回到 10-24 的已知状态），不是脚本该替人拍的事。把"该删了"变成一条会说话的输出，
比让脚本自己动手更符合本仓"不可逆动作须人确认"的既有纪律。

**可证伪**：`--self-test` 从 5 项增到 8 项，新增 3 项专测分类：bundle 全留 /
同月 5 份 tar → 留 3 候 2（写成"全保留"会红）/ 跨月留锚点（写成"只留 3"会红）。

## 四、快照清单：把追溯放回 git，把字节留在盘上

**病**：`prune()` 把超期快照移到 `_trash/snapshots-archive/`（不入库）。字节在本机，
但 git 里没有任何记录 —— 新 clone 只看到 3 个快照，看不出历史上打过 215 份。

**修**：`--catalog` 生成入库清单 `snapshots/CATALOG.json`（43.7KB / 215 条）：
名字、标签、创建时间、文件数、**当前位置**（`snapshots` / `_trash/snapshots-archive` / `missing`）。
`snapshot()` 与 `prune()` 结束后**自动刷新** —— 清单若只在人工记得跑时更新，
它会在下一次 churn 之后立刻变成过期事实（正是本次要修的病）。

两条刻意的设计：
- **累计而非快照式**：合并上一次内容；两个目录里都消失的快照保留条目并标 `missing`
  + `last_seen_*`。只写"现在盘上有什么"的话，这份文件只是 `ls` 的缓存。
- **不写 `generated_at`**：每跑一次就改一行时间戳 = 每次提交都带无信息 diff（churn 的另一半）。
  "清单何时产生"由 git commit 时间回答，不需要第二个真源。

**可证伪**：`--self-test` 从 11 项增到 16 项，含"鬼条目被标 missing"（删掉合并逻辑即红）、
"计数 = 目录数"、"排序确定"。
