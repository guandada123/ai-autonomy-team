## 二、发现项

### F1（中）`item_gate.py` 把多席位按「全对」计分，不是多数票

首版对多文件臂记 `per = 1.0 if all(hits) else mean(hits)`，打印时再按 `per == 1.0` 计数 →
等价于「三席全对才得分」（unanimity），而 `score_v2` 用的是多数票。

| 口径 | v3 的 seats 得分 |
|---|---|
| 首版（unanimity） | 0.500 |
| 修正后（多数票） | **0.556**（Q08 三席分裂，未成票，不计分母） |
| `score_v2` | 0.556 |

**危害不是数字大小，是方向**：低估席位 → 更容易判「常数胜出」。本次结论没被推翻
（0.700 > 0.556 仍成立），但如果某批题多数票 8/10、全对只有 5/10，这个闸会**误报**。

已修：缺省按席位多数票（≥2 票且过半，凑不出记 None 不计分母），`--as-repeat` 才按重复运行算 `pass^1`/`pass^k`。
回归：v2 第四轮 seats 仍 1.000 且仍判 26/26 饱和；v3 seats 0.556，与 `score_v2` 一致。

### F4（中，审计中追加发现）launchd 守卫用 `test -f`，等于没有守卫

原 plist 用 `[ -f 脚本 ]` 判断仓库可不可用。对照实验（同一 launchd 任务内，先读内盘再读外置卷）：

```
内盘读: 1259 项                      ← launchd 本身正常
外置卷 ls: Operation not permitted    ← 外置卷被 TCC 挡住
test -f : yes                        ← 文件"存在"
test -r : yes                        ← 文件"可读"（假的）
head -c1: no                         ← 真读一个字节才暴露
python读 : Traceback … EPERM
```

**`-f` 与 `-r` 在 TCC 下都撒谎，只有真读一个字节有效。** 已把守卫改成
`head -c 1 … >/dev/null 2>&1`，并在安装脚本里补「装好 ≠ 能跑，请先 kickstart 验证一次」。

### F5（结论强度升级）「TCC 挡住 launchd」原来只是推断

上一轮我凭一条 `Operation not permitted` 就下结论。本次补了对照：同一个 launchd 任务里
内盘可读、外置卷不可读 → 排除「launchd 配置错/路径错」，确认为卷访问限制。
另外发现 `ls` 被拒但 `test -f` 通过，说明限制是**读内容**而非**看目录项**。
