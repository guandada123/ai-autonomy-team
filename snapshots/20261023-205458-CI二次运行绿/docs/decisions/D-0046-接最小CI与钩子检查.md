# D-0046 · 接最小云端 CI，并把「推送钩子已装」纳入接手验收

- **日期**：2026-10-23 20:46
- **决策者**：用户（D-0045 遗留项拍板时选择「接最小 CI + 补钩子检查」）
- **操作分级**：🟡 中（新增一条持续调用外部 runner 的路径；不传数据、不含密钥、不改仓库内容）
- **状态**：生效

## 决定

两件事一起做，因为它们堵的是**同一类洞的两个方向**：

1. **新增 `.github/workflows/selftest.yml`**：`push` / `pull_request` / 手动触发，
   在 `ubuntu-24.04` 上跑 `make selftest`（含 A–H 门禁与 50 项全量回归）；
2. **`verify_handover.py` 增加第 6 项「推送钩子」**：存在、可执行、指向本仓
   `scripts/pre_push_scan.py`，缺一即 FAIL 并打印 `make hooks`。

## 为什么两件都要（少一件就留一个方向的洞）

| 层 | 时机 | 能拦什么 | 缺失时谁红 |
|---|---|---|---|
| 钩子（本地） | `git push` **之前** | 密钥泄漏、远端被误设 public | 没人红 → 所以补第 6 项 |
| CI（云端） | 推送**之后** | 干净环境跑不起来的提交（漏提交、隐式依赖本机文件） | GH 上红，但已经推出去了 |

两者不可互替：**CI 拦不住密钥**（推上去时数据已经离开本机），
**钩子证明不了干净环境能跑**（它就在本机，本机有一切残留）。

## CI 为什么值得接（唯一不可替代的作用）

它每次推送都在**一台没有本机残留的机器**上证明「只拿这个仓库，东西能跑」。
这不是假想风险：2026-10-23 之前 `snapshots/` 住在 `_trash/`，`_trash/` 被 gitignore，
导致 H 项在干净环境**必红**（`D-0009` / `L-0009` 类）。这类错误的共同点是
**在本机永远绿**——只有干净环境能抓到，而干净环境不能靠"记得手动 clone 一次"。

## 明确不做的事

- ❌ **不把 `verify_handover` 放进 CI**：第 6 项查的是本机钩子，CI 上必然没有，
  放进去等于让 CI 恒红（假信号）。CI 只跑 `selftest`（脚本自检 + 门禁）。
- ❌ **不用 `ubuntu-latest`**：固定 `ubuntu-24.04`。浮动标签会在某天静默换镜像，
  把「哪天开始红的」变成不可归因（同族教训：`gitleaks-action@v3`）。
- ❌ **不用浮动 action tag**：`actions/checkout` 固定到 commit
  `11bd71901bbe5b1630ceea73d27597364c9af683`（v4.2.2）。
- ❌ **不给任何 secret**：门禁纯标准库、不联网；`gh` 只出现在 `pre_push_scan.py` 里，
  且离线时只告警不拦截。
- ❌ **不在 CI 里跑备份**：`make backup` 依赖本机与外置盘，云端跑等于备份到不存在的地方。

## 可证伪性（第 6 项，2026-10-23 20:44 实测）

| 场景 | 预期 | 实测 |
|---|---|---|
| 原仓库（钩子 19:09 已装） | 6/6 | `[PASS] 6/6`，第 6 项「已装且指向 pre_push_scan.py」 |
| 复制一份并 `rm .git/hooks/pre-push` | 第 6 项红、rc≠0 | `rc=1`，`[FAIL] 1/6 项未通过：6 推送钩子`，明细「未安装（.git/hooks/pre-push）→ 跑 make hooks」 |
| 在副本里 `make hooks` 后重跑 | 转绿 | `rc=0`，6/6 |

也就是说这条检查既能红、也能被修复动作转绿——不是恒真。

## CI 首跑：11 秒就红，根因不在代码（2026-10-23 20:52）

| 项 | 实测 |
|---|---|
| run | `39956591150`，11 秒，`failure` |
| 失败点 | `make_backup.py --self-test`：4 项挂第 1 项「完好的 bundle 应通过」（3/4） |
| 根因 | `actions/checkout` 默认 `--depth 1` 浅克隆；浅仓库里 `git bundle create --all` **能返回成功**，但产出的 bundle 缺历史边界对象、clone 不回来 |
| 复现方式 | 本地 `git clone --depth 1` 后跑同一命令，输出与 CI **逐字相同** —— 不是 Linux/macOS 差异 |
| 修法 | ① workflow 加 `fetch-depth: 0`（门禁要验完整仓库，就给完整仓库）；② `make_backup.py` 前置拒绝浅克隆（rc=2 + `git fetch --unshallow`），原来只在下游报「clone 失败」，看不出原因 |

这条红是**值得的**：它证明 CI 不是本地门禁的复读机 —— 它跑在一台前提不同的机器上，
把「本地绿 ≠ 这个 commit 绿」当面演示了一次（`L-0015`）。

**二次运行（修后）**：run `39956873272`，13 秒，`success`。机器为 `ubuntu-24.04` +
Python 3.12.3；A–H **8/8**、回归 **50/50**、H 项快照与真源一致 ——
即「只拿这个仓库，在别人的机器上也能跑」不再是一句声称，而是每次推送都被验证。

## 风险

| # | 风险 | 处置 |
|---|---|---|
| 1 | 全新 clone 首跑 `make handover` **必然红在第 6 项** | 这是真话不是误报；README「30 秒上手」已写明先 `make hooks`；D-0029 的历史表述（5 项）不回溯改，由本决策记录变更 |
| 2 | GitHub Actions 分钟数（私有仓库计费） | 单次约 1–2 分钟；`concurrency` 取消同分支旧跑；只跑 push/PR |
| 3 | CI 红但本地绿，可能被当成噪音 | 红的意义正是「干净环境跑不起来」，本地绿不能反驳它；排障入口写进 DEPENDENCIES |
| 4 | 第三个动作依赖（actions/checkout）供应链 | 固定 commit SHA，不用 tag；`persist-credentials: false` |

## 重新评估的触发条件

1. CI 单次超过 5 分钟 → 拆 job 或砍回归（先看是不是 `regress` 变重）；
2. 仓库转为公开 → 需重跑全部历史的密钥扫描（公开后历史即公开）；
3. 要在 CI 里做发布/部署 → 属于新的信任边界，须另立决策。
