# D-0032 · 依赖策略：全项目可用，不逐项确认；迁移包保持零依赖

- **日期**：2026-10-22 13:38
- **决策者**：用户（原话「允许在 Claw 侧引入外部依赖；不限于 Claw，所有项目中只要可用的依赖都可以直接使用，无需逐项确认」）
- **操作分级**：🟡 中（放开依赖会改变供应链面）
- **状态**：已采纳

## 决策

| 范围 | 策略 |
|---|---|
| **所有项目（Claw / QTS / StockInsight / PMF / EAK / wechat_api 等）** | **允许直接引入外部依赖，无需逐项确认** |
| **`migration-package`（迁移包本体）** | **仍保持零第三方依赖**（纯标准库） |

## 为什么迁移包例外

不是保守，是**它自己的验收条件决定的**：

| 事实 | 出处 |
|---|---|
| G4 要求「凭它能在另一台机器重建并继续开发」 | D-0002 §效果评估 |
| `verify_handover.py` 第 1 项就是「py≥3.9 且第三方依赖命中 0」 | `scripts/verify_handover.py` |
| 一旦引入依赖，换机需先建虚拟环境、锁版本、处理镜像源 | 工程常识 |

**取舍**：包外随便用，包内不能脏。这样既拿到工程效率，又不破坏自包含性。

## 落地约束（授权之外的护栏）

放开依赖 ≠ 不做检查。以下四条仍然生效：

1. **新增依赖必须写进依赖清单**（`pyproject.toml` / `requirements*.txt`），不许裸 `pip install`；
2. **锁版本**（QTS/StockInsight 已有 lock 文件；Claw 用 `requirements.txt` 固定）；
3. **许可证核对**：本次调研已发现两个坑——
   - `microsoft/autogen` 的 API 字段是 CC-BY-4.0，代码实为 `LICENSE-CODE`=MIT；
   - Phoenix 是 Elastic-2.0（非 OSI），不能进"开源依赖"清单。
   新增依赖前须确认 `LICENSE` 实际文本，不看 GitHub 的 `spdx_id` 字段；
4. **迁移包 CI 仍以 `verify_handover` 为准**：包内出现第三方 import 即判红。
